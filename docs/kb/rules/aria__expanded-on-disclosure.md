# `aria/expanded-on-disclosure`
- **Severity:** warning
- **Scope:** node
- **Satisfies:** `wcag22:4.1.2`, `wcag21:4.1.2`
- **Applies to:** .html, .htm, .tsx, .jsx
## What it checks
Disclosure triggers (buttons / links / role=button that toggle a collapsible region) must carry aria-expanded so assistive tech can announce the open/closed state.
## Why it matters
WCAG 4.1.2 requires that a component's state be programmatically determinable. A disclosure trigger with no aria-expanded is announced without its open/closed state — the user can operate the control but cannot tell whether the region they just toggled is now visible or hidden. Real-world evidence: widely-used component libraries ship disclosure triggers (Bootstrap's `data-bs-toggle="collapse"` links, dropdown buttons, accordion headers) without aria-expanded; the static scanner catches these because the shape of a disclosure trigger is detectable even though runtime behavior isn't.
## Normative quote
> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.
## Good example
```tsx
<button aria-controls="panel-1" aria-expanded="false">Details</button>
<div id="panel-1" hidden>…</div>
```
## Bad example
```tsx
<button aria-controls="panel-1">Details</button>
<div id="panel-1" hidden>…</div>
```
