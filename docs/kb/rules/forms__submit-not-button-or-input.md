# `forms/submit-not-button-or-input`
- **Severity:** error
- **Scope:** node
- **Satisfies:** `wcag22:4.1.2`, `wcag21:4.1.2`, `wcag22:3.3.2`, `wcag21:3.3.2`
- **Applies to:** .html, .htm, .tsx, .jsx
## What it checks
A <form> with no <button>/<input type=submit> but containing an <a> styled as a button uses the anchor as the apparent submit control — wrong role for assistive tech.
## Why it matters
Sighted users see a button, click it, the form submits. Screen readers announce 'link, Login' — and link activation does not fire the form's submit handler, action attribute, or implicit Enter-on-input submission. The author's HTML even tells you what they meant: in real templates we see comments like 'Change this to a button or input when using this as a form' sitting above an `<a class="btn">`. The anchor was a stand-in that never got swapped. Both 4.1.2 (wrong role) and 3.3.2 (no labeled submit affordance) apply.
## Normative quote
> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined.
## Good example
```tsx
<form action="/login" method="post">
  <label>Email <input type="email" name="email"></label>
  <button type="submit" class="btn btn-primary">Login</button>
</form>
```
## Bad example
```tsx
<form action="/login" method="post">
  <label>Email <input type="email" name="email"></label>
  <!-- Change this to a button or input when using this as a form -->
  <a href="index.html" class="btn btn-primary">Login</a>
</form>
```
