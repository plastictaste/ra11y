# `aria/progressbar-value-range`
- **Severity:** error
- **Scope:** node
- **Satisfies:** `wcag22:4.1.2`, `wcag21:4.1.2`
- **Applies to:** .html, .htm, .tsx, .jsx
## What it checks
Progressbars (role='progressbar' or native <progress>) must declare coherent aria-valuenow / aria-valuemin / aria-valuemax values so assistive tech can announce progress.
## Why it matters
WCAG 4.1.2 requires that the value of a user-interface component be programmatically determinable. A progressbar with no aria-valuenow is announced as 'progress bar, (blank)'. A progressbar with aria-valuenow=150 and aria-valuemax=100 is announced as '150 percent' — a meaningless reading that confuses users and defeats the purpose of the widget. Widely-used component libraries (Bootstrap's .progress pattern) ship examples with both shapes; the scanner catches them because the invariant is statically checkable against literal attribute values.
## Normative quote
> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.
## Good example
```tsx
<div role="progressbar" aria-valuenow="30" aria-valuemin="0" aria-valuemax="100" aria-label="Upload"></div>
```
## Bad example
```tsx
<div role="progressbar" aria-valuenow="150" aria-valuemax="100"></div>
```
