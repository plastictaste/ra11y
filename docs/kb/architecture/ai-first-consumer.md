# AI-first consumer model

ra11y's primary consumer is an AI agent calling the MCP tools — not a human reading a dashboard. CLI and formatters exist, but the design center is the agent. Several common tooling defaults invert under this assumption; treat the rules below as load-bearing when triaging field reports or designing new surfaces (MCP tools, response shapes, reports, formatters).

This doctrine lives here (rather than in CLAUDE.md) so it loads automatically when editing code that shapes MCP tool responses — `src/mcp/**`, `src/reports/**`, `src/output/**`, `src/review/**`, plus the authoritative shape-owning files `src/types/violation.ts`, `src/types/review.ts`, and `src/engine/scanner.ts` — via the path-scoped rule at `.claude/rules/mcp-response-shapes.md`.

## Rules

- **Surface, don't suppress.** Agents read every candidate in milliseconds; reviewer fatigue isn't the constraint a human-facing tool optimizes around. False positives a human would tune out are cheap for an agent to dismiss with one file read. Suppression discards signal the agent would use to triage. Default to surfacing with enough context for the agent to investigate.
- **Don't downgrade priority to hide things.** "Mark as low priority" is a UX lever for human attention budgets. Agents don't have one — they just sort. Surface honestly and let the agent rank by criterion + reason + context.
- **Verbose meta is signal, not clutter.** `configSource`, `activeNativeWrappers`, `rulesEvaluated`, per-extension file counts — these are scan-confidence telemetry the agent actively uses to decide whether the scan had teeth and what to call next. Don't trim them to look terse. (Note: `configSearchedFrom` is present-when-meaningful — omitted when it would just echo the caller's `cwd` or a `scanned.root` already in the response.)
- **Review *candidates*, not assertions.** For manual criteria, return locations + a short `reason` that frames the question. Don't try to be smart about "what the user really meant" — agents are better at that than heuristics.
- **One tool call should answer "what next?"** Each response carries `nextStep` hints, criterion IDs, and counts that match the other tools' counts. Cross-surface drift (`scan` says 21, `checklist` says 4) forces wasted round trips; invariants like the manual-review-count test exist to prevent this.
- **Default-exclude globs are suppression too.** Growing `DEFAULT_EXCLUDED_PATTERNS` in `src/input/discover.ts` to "reduce noise" from scans is the same mistake as downgrading severities or silencing finders — it just happens one level earlier in the pipeline. An agent can dismiss a finding whose path contains `test/fixtures/` or `stories/` in one read; it can't un-suppress a file that never got parsed. Only add an exclusion when findings in that path tree are *definitionally wrong for any consumer* (generated code, `.min.*`, vendor dumps). "Most people don't want to see this" is a human-attention argument, not a correctness one; it is not sufficient. If an existing entry in the list can't clear that bar, it's a bug, not a precedent.
- **No heuristic suppression, even for spec carve-outs.** WCAG's exemptions (logotypes, process-page exception, essential presentation) are conceptual rules — *detecting* whether a given element falls under one is a heuristic on weaker evidence than the agent has. An `<img>` with `alt="Acme logo"` might be a brand mark, or it might be a product shot the author mislabeled. A repo with three HTML files might be an SPA shell, or it might be the start of a content site. Our attribute-level snippet is not enough to make that call; the agent reading the whole file is. Encoding a heuristic as suppression replaces honest "please verify" with false confidence and risks silent false negatives on real violations. The deterministic escape hatch is the source-level disable pragma (`<!-- ra11y-disable wcag22:1.4.5 -->` / `{/* ra11y-disable wcag22:2.4.5 */}`) — once an agent investigates and dismisses, the pragma makes that dismissal durable. No guessing required. If a specific review candidate keeps drawing field-report complaints, the fix is better `reason` text (so the agent dismisses faster), not a finder-level carve-out.
- **Labeled buckets are suppression too.** "Splitting findings into a primary list and a deprioritized/verbose/likely-X bucket" is the move that looks like labeling but behaves like suppression — once consumers learn the bucket is skippable by default, the silent-miss failure mode is identical to hiding the finding outright. A bucket is only honest when its label is *provable from the code* (e.g. `likelyIrrelevant` for "no `<video>` elements in the scanned files" — a deterministic fact). Filename patterns, identifier patterns, and spec-exemption guesses do **not** earn a bucket. They earn reason-text enrichment, which the agent reads per-candidate and acts on individually. The test before adding a new bucket: would the label be correct 100% of the time from the evidence the scanner has? If it's a heuristic, the answer is no.
- **Failure modes are asymmetric; the rules above lean against the cheaper failure.** Over-surfacing → the agent dismisses in one read, at a few seconds' cost, and the judgment stays visible. Under-surfacing → a real violation never reaches the agent; the user doesn't know it happened; the miss is silent and non-reversible. When a reasonable-sounding field report asks for "less noise" in a way that would hide findings, remember the costs are lopsided — and that "this looks tractable, we can split the difference" is where the silent-miss regressions live. Durable rule: when in doubt, surface and annotate; never bucket-then-filter.
- **Numeric-threshold heuristics are suppression.** "Auto-dismiss when the setTimeout duration is ≤ 5 seconds," "only flag when the image is ≥ 100px wide," "require at least N call sites before reporting" — thresholds dressed up as precision checks are the same heuristic-suppression move as filename-pattern matching. The threshold picks a point on a continuous axis and hides everything on one side of it; the silent-miss failure mode is identical. A real session timeout of 4.5 seconds is indistinguishable from a debounce of 4.5 seconds from static analysis alone, and the agent reading the surrounding code is the only correct arbiter. Encode the duration/size/count in the `reason` text as additive context ("setTimeout with 2000ms literal"); let the agent decide.
- **Don't duplicate capability the agent already has.** Before adding in-tool analysis — cross-file identifier resolution, path walking, fuzzy name matching — ask whether the consuming agent can do the same thing with Read + Grep. If yes, the tool doing it risks being redundant at best and confidently wrong at worst: in-tool heuristics produce output the agent can't tell to mistrust ("`handleChange` defined at line 42, body is clean" is a liability the first time line 42 is a shadowed binding). The tool's job is to *point* — file, line, pattern; the agent's job is to *investigate*. This inverts the default for human-facing tools, where doing more in-process is usually better. Reflex check every time feedback asks for "smarter" analysis in a finder.
- **Interrogate the problem before accepting the solution's shape.** When feedback says "add a show_X tool" or "we need a Y flag," the first check is whether the capability already exists in a tool or call that wasn't discovered. Field reports carry the *problem* the reporter hit, not evidence of a structural gap. Accepting the solution's shape short-circuits that check and creates tool-bloat — more shapes on `tools/list`, more drift surface, more overlap — paid even when the underlying problem was documentation. If the capability exists but is hard to find, sharpen the tool description; if it doesn't, then design.
- **Ambiguous field shapes are dishonest.** A field that is sometimes populated and sometimes `""` (or `null` used as "unknown") forces the agent to re-read and disambiguate whether the value is unavailable or genuinely empty — and because agents usually treat the empty value as real data, the downstream mistake is silent. Omit the field entirely when it has no meaningful value; use conditional spreads at the response-assembly site (`...(x ? { field: x } : {})`). `newText: ""` under `kind: "edit"` is the canonical mistake; `snippet: ""` alongside a populated `sourceContext` is the same bug in another place. The test: if a downstream consumer has to ask "did I get an empty answer or no answer?", the shape has failed. This applies only to optional fields — schema-required fields stay populated; the shape signals "present-when-meaningful."
- **Zero-output success is ambiguous failure.** A response shaped like "success + 0 findings / 0 files scanned / empty list" is indistinguishable from "the input never reached the tool." The canonical case: `scan_project({ cwd: "/tmp/wrong-path" })` returns `{ filesScanned: 0, totalFindings: 0 }` with success — the agent concludes "clean codebase" when the reality is "tool never ran," and the miss is non-reversible once the agent acts on it. When the input or configuration is plausibly malformed — nonexistent `cwd`, zero parseable files, no config resolved, CSS absent but Tailwind classes detected, template files parsed as literal — emit a response-level `warnings: string[]` (structured codes preferred: `scanned_zero_files`, `root_source_defaulted`, `no_config_found`, `tailwind_detected_css_undercounted`, `template_files_parsed_as_literal`). The test: can a caller distinguish success-with-nothing-to-do from success-with-nothing-ran by reading the response alone? If not, the shape is dishonest. This is the response-level analogue of the per-field rule above.
- **Composite headline counts are dishonest.** A top-level counter like `manualReviewRequired: 21` reads as "this much work to do," but often sums categorically different sub-buckets — grounded candidates with file:line vs. bare-criterion prompts, mechanical edits vs. prose-only guidance. Agents budget against the headline, and the composite inflates or misclassifies the work. If a counter names one concept, it must count one kind of thing; when two kinds exist, split into two counters (`actionableManualItems` + `untargetedCriteriaForProject` on project-walk surfaces; the per-file twin `untargetedCriteriaForFile` ships from `scan` / `scan_file` so the slice is explicit on the wire). Do NOT keep the composite as a sibling next to the per-kind tally — two counters both framed as "how many of X" will disagree whenever they measure different slices, and the disagreement is silent. Canonical case: `plan.safeEditsAvailable: 14` shipped next to `plan.fixesByClass.mechanical: 266` — an 18× disagreement that forced the agent to pick one; fix was to drop the composite. Labels on sub-fields aren't enough if a headline still sums them. `plan.totalFindings` was removed (not renamed) once the same disagreement surfaced summing source vs. buildArtifact lanes — deletion is the durable answer rather than label-stretching. The same shape recurred on `plan.untargetedCriteria`: one field name shipped two scope-distinct slices (project-walk N=7 vs single-file N=18 on the same corpus) — closure renamed each slice to `untargetedCriteriaForProject` / `untargetedCriteriaForFile` and dropped the bare composite.
- **Heuristic-mislabeled meta sub-fields are dishonest.** The labeled-buckets rule applies one level deeper: any `reason`-shaped sub-field on a meta entry must clear the same "provable from the code" bar as the bucket itself. `scannedBuildArtifacts[].reason: "minified"` reads as a deterministic classification — but if the predicate is a single-long-line heuristic that fires on hand-authored long-line files (template-literal islands in JSX, prop-bundle wrappers, SCSS function bodies), the label lies and the agent's downstream triage propagates the lie silently. Same applies to `templateDirectivesFound: ["handlebars-or-mustache"]` when the evidence is `${{ ... }}` GitHub-Actions in `.yml` files. Test before adding such a field: would the token be correct 100% of the time from the evidence the scanner has? If "usually," drop the token and surface the underlying signal (line-length distribution, sourcemap-sibling, hashed-filename, directive-token co-occurrence) as additive evidence. The silent miss is the agent treating mis-labeled vendor as actually-vendor and rerouting fix suggestions away from a file the user did author.
- **Heuristic emission is the symmetric twin of heuristic suppression.** The "no heuristic suppression" rule has a mirror: a rule that *emits* on speculation about composition or rendering — "When composed into a layout, will likely sit alongside another `<form>`", "the value `p` might be a session timeout", "this anchor probably toggles a sibling carousel" — is the same predicate-strength mistake in the opposite direction. Encoding low-confidence evidence as a deterministic finding (severity `error`/`warning`) leaks the heuristic's uncertainty into a slot the agent reads as "this is real." Agents budget against severity; a speculative rule fire wastes that budget the same way speculative suppression hides a real one. Test before emitting: is the predicate provable from the code in this file alone, or does it depend on guessed composition? If the latter, the finding belongs on the review-candidate surface (where `reason` text frames a question the agent verifies), not on the rule surface. Canonical case: `semantics/duplicate-landmark-unlabeled` emitting on a single unlabeled `<form>` because "it likely sits alongside another form once composed" — the composition is unobservable; the emission is dishonest. Closure path: gate the emission on confirmed sibling evidence in-file, or move the predicate to a finder.
- **Reason text and severity must agree.** When a rule's `reason` concedes the predicate it claims to violate is satisfied — "the visible text already carries the status word", "the parent `<a>` already carries the accessible name", "if standalone single-page this criterion may not apply" — the rule must not still emit at `error`/`warning`. A `reason` that contradicts its own severity is a dishonest shape: the agent budgets against severity, reads the reason, discovers the budget was wasted; worse, the contradiction trains the agent to mistrust the rule even when right. Three closure paths: (a) suppress emission on the conceding branch; (b) downgrade to a review candidate so framing matches "please verify"; (c) rewrite the reason to surface what is *actually* still in question (e.g. "color may still be the *sole* cue"). Canonical case: `color/meaning-by-color-only` emitting at `error` on `<button class="btn-danger">Danger</button>` while the reason concedes "Danger" is present. Extension to *conceded uncertainty*: a reason that hedges with `"verify the inheritance chain"` / `"runtime behavior may differ"` / `couldBeWrongBecause: [...]` while severity stays `error`/`warning` is the same shape — same three closure paths apply.
- **Cross-surface count invariant.** When the same conceptual counter ships from multiple project-rooted tools on the same input — `actionableManualItems` from `scan_project.plan` vs `checklist.summary.actionable` vs `coverage.manualWithCandidates.length`; `untargetedCriteriaForProject` from all three; `parseErrorFileCount` from `scan_project` vs `coverage` — the values must agree. Drift is silent: the agent reads the first headline, budgets against it, and notices disagreement only by chance. Each shared counter must be computed once in a shared helper; an integration test pins equality. Fields named like `countsBySurface` must actually reconcile, not multiply. Extends to *scan-confidence warning telemetry*: scope-level warnings like `scanned_build_artifacts_present` / `bulk_catalog_detected` shipping on `scan_project` but absent from `checklist` / `coverage` on identical cwd means an agent calling `checklist` first on a bulk-vendor corpus has zero signal that 996 minified files exist. Warnings whose evidence is the corpus must reach every consumer of that corpus. Closure: every project-rooted tool emits the same scope-level warning set on identical cwd, via the shared scan-confidence helper.
- **Parser-failure invalidates per-file confidence.** When a file appears in `analysisCoverage.parseErrorFiles[]` or `partialParseFiles[]`, every `perRuleCoverage` entry crediting that file must downgrade `coverageConfidence` to `"low"` / `"medium"` with a `reason` naming the parse failure (`"parse_failed"` / `"partial_parse"`). A `confidence: "high"` entry on a file the parser bailed on is the parser-side mirror of "reason text and severity must agree" — the per-rule label claims the rule observed full evidence; the recorded parse error says it didn't. Agents reading per-rule coverage as scan-confidence telemetry are silently misled. Same invariant applies to `fragmentFiles[]`: when a file is classified as a fragment (`_includes/`, `_partials/`, README.md residue), document-shaped rules (`landmark-main`, `heading-hierarchy`, `page-titled`, `lang-attribute`) must downgrade with `reason: "fragment_input_no_document_envelope"` rather than reporting `"high"` confidence that they could not honestly establish. The general rule: any classification that gates the rule's evidence model must propagate to that rule's confidence label in the same response.
- **Oversize-success is ambiguous failure.** A response that succeeds internally but whose serialized payload exceeds the MCP host token cap leaves the agent with only a host-level transport error — no `plan`, no `meta`, no `warnings`, no `nextStep`. The silent-miss is identical to zero-output-success: "ran on nothing" and "envelope evaporated" are indistinguishable. Bulk-corpus scans produced post-clip payloads still 18× over the host cap; internal mitigation (clip files, `truncated: true`, `response_token_budget_truncated`) is too late if the post-clip envelope is still over budget. When pre-serialization size estimation crosses a sentinel (e.g. 24KB), fall back to a minimum-honest envelope: keep `plan` + `meta` + `warnings: ["response_dropped_files_oversize"]` + `nextStep` (recommending scope-down), drop `files[]` rather than the whole response.
- **Routing skips that drop content are the symmetric twin of suppression.** Routing `.js` through the tsx parser silently drops plain-JS findings (parser bails on relational expressions read as JSX); failing to recurse into `innerHTML` / `insertAdjacentHTML` / `document.write` template-literal HTML islands silently drops dynamically-injected widget findings; rejecting `.xhtml` / `.mkdn` / `.erb` as `file-unsupported` silently drops valid input. The agent cannot un-skip a file the scanner refused to parse. Apply the same scrutiny to routing as to suppression: emit a structured warning (`text_source_skipped`, `binary_assets_skipped`, `js_innerhtml_template_literal_unparsed`, `parser_bailed_on_non_jsx_in_tsx_route`) so the agent can re-route or scope around it. Skipped-extension warnings are split by predicate so the actionable text-source subset doesn't get buried under binary-asset volume on bulk catalogs (a `.jpg: 1835` hiding `.php: 30` is the canonical regression).
- **Per-finding confidence must reflect per-rule coverage limitations.** When `perRuleCoverage[ruleId].coverageConfidence` is `"medium"` / `"low"` with a documented limitation reason (`cross_file_listener_resolution_not_attempted_by_rule`, `cross_file_idref_resolution_not_attempted_by_rule`, `cross_file_custom_property_resolution_not_attempted_by_rule`), every per-finding emission from that rule in the same response must propagate the limitation — either by downgrading per-finding `confidence` to match the per-rule label or by echoing the reason as additive context. Canonical case: `keyboard/handler-missing` reporting per-rule `coverageConfidence: medium` while emitting per-finding entries at `confidence: high, severity: error` against `<button>` elements wired by sibling `.js`. Same rule, same response, contradictory claims — analogous to "reason text and severity must agree" at a different layer. Closure: propagate the degradation to per-finding `confidence` OR include the reason in each finding's `couldBeWrongBecause`.
- **Reason-token suffixes must name the actual predicate.** A `reason` code suffixed `_limited_on_this_input` reads as "we tried this input and were limited" — implying a different input might resolve the limitation. When the rule has `crossFileCapable: false`, the limitation is a permanent rule-design choice, not an input hiccup. Encoding rule-design limitation as input-specific framing risks the agent wasting a re-scan. Honest suffix: `_not_attempted_by_rule` for rules that structurally never attempt; reserve `_limited_on_this_input` for rules that do attempt cross-file but were bounded by incomplete input (partial-parse, file-set-limited). Test: does the rule's design actually try the resolution this code names? If not, `_limited_on_this_input` lies. Closure renamed cross-file-listener limitation codes from rules tagged `crossFileCapable: false` to `_not_attempted_by_rule`.
- **NextStep prioritization on truncated/bulk responses must avoid first-by-filename routing.** `nextStep` / `nextStepStructured` defaults to the alphabetically-first finding when truncated or bulk-vendor-heavy. Observed routing to a visual-regression fixture, an underscore-prefixed scaffold `index.html`, and a vendor stylesheet already classified as `scannedBuildArtifacts`. The agent following `nextStep` wastes a `suggest_fix` call on non-actionable input — a vendor file, a fixture with no consumer, or a scaffold dir with placeholder content. Per "one tool call should answer 'what next?'", the first-call recommendation must reflect impact, not lexical order. Closure: when `truncated: true` OR when the candidate is in `scannedBuildArtifacts`, route `nextStep` to the highest-firing rule's first non-vendor finding, OR to a "scope down via `additionalPaths`" suggestion.
- **NextStep prose and structured channels must agree.** Every project-rooted response ships two adjacent next-step fields: `nextStep` (free-text prose the operator might read) and `nextStepStructured` (a `{ tool, args }` shape the agent will execute). When these channels disagree silently — prose says "scope down: narrow `cwd` or pass `restrictToPaths`", structured says `{ tool: "explain_rule", args: { ruleId } }` — the agent's executed handoff contradicts the prose-stated intent, and the silent-miss failure mode is identical to the cross-surface count invariant: each channel looks locally correct, the disagreement is invisible from one channel alone, and the budget burn is silent. Multi-corpus observation: scan_project on a vendor catalog ships prose `Scope down further before re-calling: pass a tighter cwd... use restrictToPaths` alongside `nextStepStructured: {tool: "explain_rule"}`; bootstrap on a bulk-demo corpus ships prose recommending narrowing alongside structured `{tool: "scan_project", args: {groupBy: "firstChildDir"}}` (aggregation, not narrowing); scan_file on a confirmed-vendor file routes structured back to a project-rooted tool that the same caller already established was oversize. Closure: derive both channels from the same predicate at response-assembly time — when prose advises a scope-narrowing call, the structured field MUST encode that same call's tool + args; when prose advises a different next move, the structured field MUST encode that move. Pin via integration test that asserts: for every response shipping both fields, the structured tool name is consistent with the action verb in the prose's first sentence (`scope down` → `scan_project` with restrictToPaths/additionalPaths; `inspect this finding` → `suggest_fix`; `tune the rule` → `explain_rule`). Reachable from "One tool call should answer 'what next?'" and from the cycle-termination invariant, but the channel-agreement axis is its own surface.
- **NextStep handoffs must terminate at a narrowing tool, never form a cycle between transport-failing siblings.** When two project-rooted tools both transport-fail at the host token cap on the same input AND each tool's `nextStepStructured` routes the agent at the other, the agent is stuck in a circular handoff with no narrowing path in the cycle. The canonical case: on a bulk-vendor corpus, `checklist.nextStepStructured.tool: "coverage"` while `coverage.nextStepStructured.tool: "checklist"` — both surfaces ship oversize on the same scope, and neither cycle exit narrows scope. The silent-miss failure mode is identical to circular `import` resolution: each step looks locally correct, the cycle is invisible from one tool's response, and the agent's budget burns alternating round trips. Closure: on every project-rooted tool, when truncation or oversize sentinel is signaling AND a `bulk_catalog_detected` / `response_dropped_files_oversize` warning is in the response, `nextStep` MUST route to a scope-narrowing call (`scan_project({restrictToPaths: [...]})` or `scan_project({additionalPaths: [...]})` with a single sub-tree argument), never to a sibling tool that ships from the same scope-classifier. Test: every cross-tool `nextStepStructured.tool` recommendation, traced one hop further on the same cwd, must reduce input scope or reduce the rule set; never echo the parameters that just produced the truncation. Reachable from "One tool call should answer 'what next?'" but the cycle-detection invariant is its own surface.
- **Truncated containers must rename or sentinel, not retain.** When a top-level container (`meta`, `analysisCoverage`, `scannedBuildArtifacts`, `perRuleCoverage`) is gutted by truncation, retaining the field name while stripping sub-fields is dishonest in the same way as ambiguous-empty-string. The agent reads `meta` and finds 9 trivial scalars; it cannot distinguish "no scan-confidence concerns" from "meta block was clipped." Observed on `meta` (9 keys remained, 10+ stripped under `response_meta_truncated`) and on `coverage.perRuleCoverage[]` (empty under truncation while `scan_file` on same input ships ~95 rows). Closure paths: (a) rename the surviving field on truncation (`metaTruncated`, `perRuleCoverageTruncated`); (b) replace each absent sub-field with a `{truncated: true, reason: "..."}` sentinel; (c) pair with `warningsDetails.<warning>.fieldsDropped: [...]` so absence is visible from the warning channel. General rule: signal the discard at the field level — name retention without sentinel looks like a populated container.
- **Per-call shape must agree with per-class plan tally.** When `plan.fixesByClass.mechanical: N` advertises N findings as having a safe edit, every `suggest_fix(ruleId, file, line)` resolving to one of those N must return `kind: "edit"` with materialized `oldText`/`newText`. The earlier `meta.mechanicalInPrinciple: true` annotation on `kind: "guidance"` responses was the canonical contradiction — two sibling fields answered "is a mechanical edit available" with opposite values; agents reading the plan tally first budgeted against a fixable count the per-call surface wouldn't honor. Closure paths: (a) when `kind: "guidance"` is the honest per-call shape, deduct from `plan.fixesByClass.mechanical` (re-tag rule's `fixClass` from `mechanical` to `verify-in-source`) — callers wanting apply-now subset sum `mechanical + verifyInSource` off the structured tally; (b) when the rule genuinely emits a deterministic edit, materialize `kind: "edit"`. Integration test pinned by `tests/integration/suggest-fix-plan-tally-parity.test.ts`. Per-call analogue of "Composite headline counts are dishonest."
- **Reason / priority / fix-description must agree across all three channels.** The "Reason text and severity must agree" rule extends to two more channels: review-candidate `priority` (parallel to severity for manual-review) and per-finding `fix.description` (parallel to `reason` for suggest-fix). A candidate at `priority: "high"` whose reason concedes "if standalone single-page or SPA, criterion may not apply" is the candidate-priority analogue. A finding at `severity: "error"` whose `fix.description` instructs "Cross-file check: grep the selector in your HTML to confirm" is the fix-description analogue — description concedes the predicate may not hold while severity claims it does. Closure paths: parse for hedging tokens (`may not apply`, `only if`, `verify…before`, `Cross-file check: grep`, `confirm…isn't`) and either (a) downgrade attention-budget signal (severity → warning, priority → medium/low), (b) move to review candidate, or (c) perform the cross-file check when the scanner has the evidence. General rule: every attention-budgeting channel (severity, priority, confidence, fix.description verbs) must agree with the reason text it ships alongside.
- **Empty `warningsDetails.<code>: {}` is dishonest.** A warning code declared in `warnings[]` whose corresponding `warningsDetails.<code>` ships as the empty object `{}` denies the agent any way to triage what the warning measures — which files, how many, what predicate. The empty-object payload is the warning-channel sibling of the ambiguous-empty-string per-field rule and the truncated-container name-retention rule: an agent reading the warning name infers "this warning fired with specifics I can act on" but the specifics are absent, and the silent-miss failure mode is identical (the agent budgets against a warning whose payload is unactionable). The multi-corpus sweep observed this on `parser_bailed_on_non_jsx_in_tsx_route` and `parser_bailed_zero_findings` shipping `{}` payloads on multiple corpora, denying the agent any per-file file-list to scope around. Closure paths: (a) populate the details payload (file list, count, evidence, reason) at emit time; (b) omit the warning code from `warnings[]` entirely if there's nothing actionable to ship; (c) consolidate with an existing more-specific warning code that already carries a payload. Never ship the code with an empty payload — the warning channel is for the agent to act on, not to acknowledge.
- **Per-tool lane and warning-set classification must agree.** When the same file or cwd is observed by `scan_project`, `scan_file`, `checklist`, and `coverage`, the lane classification (`scanKind: "source" | "buildArtifact"`), warning-set, and minimum-honest-envelope behavior must agree across all four. The cross-surface count invariant covers numeric drift; this bullet covers structural drift: a file that `scan_project` classifies under `scannedBuildArtifacts` ships as `source`-lane findings when the agent calls `scan_file` on the same path; corpus-level scan-confidence warnings (`bulk_catalog_detected`, `response_dropped_files_oversize`, `response_token_budget_truncated`, `truncated_files_dropped`, `text_source_skipped`, `binary_assets_skipped`, `js_innerhtml_template_literal_unparsed`) ship from `scan_project` but silently absent from `checklist`/`coverage` on identical cwd; the minimum-honest envelope (drop `files[]`, keep `plan` + `meta` + `warnings` + `nextStep`) implemented at `scan_project` is absent at `checklist` and `coverage`, so an oversize bulk-vendor scan succeeds at the project surface and transport-fails at the manual-review surface. An agent that calls `checklist` first on a bulk corpus, or `scan_file` directly on a vendor stylesheet, gets a different mental model of the same input than `scan_project` would have given. The multi-corpus sweep observed all three drifts simultaneously on bulk-vendor corpora. Closure: a single shared scope-classifier helper consumed by all four project-rooted/file-rooted tools — same lane labels, same warning set, same envelope ceiling, same fallback — pinned by an integration test on identical cwd.
- **Per-finding identifiers must be addressable, not collision-prone.** A `findingId` that resolves to multiple distinct file:line locations within the same response breaks the per-finding addressability contract that `suggest_fix(findingId)` and the source-level disable pragma both depend on. The canonical regression: a single `findingId` scoped to `(ruleId, file)` covers a dozen separate emission lines (lines 36, 48, 60, 87, …) — calling `suggest_fix` on that id resolves ambiguously, and an agent that suppresses on the id silences sibling lines it never read. This is the per-finding analogue of the "ambiguous field shapes" rule: the field's name promises one shape (a unique address) and the data delivers another (a one-to-many bucket). The silent-miss failure mode is identical — the agent acts on the first interpretation and the divergence stays invisible. Closure paths: (a) make `findingId` collision-free by including the location coordinate in the hash input (rule + file + line + column), so each emission gets a distinct id; (b) if a per-rule-per-file group identifier is genuinely useful for batch operations, rename it to `findingGroupId` and ship per-emission `findingId` alongside — two fields, two shapes, neither of them lying. Test before shipping: every `findingId` in a single response must be unique, and the per-call surface must address one emission per id.
- **Sibling fields naming the same concept must use one shape.** The "ambiguous field shapes are dishonest" rule extends to a cross-field-redundancy axis: when three or four sibling fields name the same conceptual quantity in three different shapes — a scalar count, a parallel array, a parallel scalar twin, an empty container of yet a fourth shape — the agent reading the response must reconcile silently. The canonical regression: a coverage payload ships `untargetedCriteria: 7` (scalar) alongside `untargetedCriteriaList: [...]` (the array form of the same count) alongside `criteriaUntestable: 0` (a parallel scalar twin) alongside `untestableCriteria: []` (the empty-array form of that twin) — four fields, two concepts, four shapes. Each individual field is well-formed, but the sibling set forces the agent to pick a canonical reading and the choice is invisible. Same shape recurs on `scssUnresolvedVariableFiles: []` + `buildArtifactEntries: []` + `buildArtifactsMetaField: {}` — three different empty containers for an "absent on this corpus" state. Closure paths: (a) one shape per concept — pick the array form, derive the scalar count at read time (`array.length` is honest); (b) when scalar and array genuinely disagree (the scalar measures a different slice than the array), rename so the names reflect the difference and document the asymmetry; (c) omit the field via conditional spread when its meaningful value is absent rather than retaining an empty container alongside its scalar twin. The general rule: a downstream consumer should not have to ask "did I just read the same number twice in three different places?"
- **Truncation reporters must reconcile across warnings.** When a single response carries multiple warning codes that report on overlapping truncation events — `response_meta_truncated.fields: ["analysisCoverage.fragmentFiles"]` listing 2 fields, `response_dropped_files_oversize.metaFieldsDropped: [...]` listing 9, plus a third top-level scalar `metaArrayTruncated: true` — the agent gets three competing narratives about what was truncated. The "truncated containers must rename or sentinel" rule covers the field-level case (one container losing sub-fields silently); this bullet covers the warning-channel case (multiple codes describing the same truncation pass with non-aligned counts and overlapping scopes). Each warning is internally well-formed, but the agent calling the response cannot answer "what is the canonical list of dropped fields here?" without cross-referencing all three reporters and picking a winner. The silent-miss failure mode is identical to the cross-surface count invariant — the first reporter the agent reads sets the budget, and the others' disagreement stays invisible. Closure paths: (a) one canonical truncation reporter per scope (meta-level / files-level / arrays-level) and let the others link to it via `seeAlso` rather than duplicating the field list; (b) when multiple codes legitimately fire (oversize-driven drop + meta-only clip from independent paths), require their scope sets to be disjoint and named — `response_meta_truncated` covers meta-only clipping, `response_dropped_files_oversize.metaFieldsDropped` only the files-array overflow path; (c) if a top-level scalar like `metaArrayTruncated` exists, it must point to the warning that owns the detail, not stand alone as a third overlapping signal. The general rule: every truncation event reaches the agent through one canonical channel, and parallel channels reconcile by reference rather than by independent enumeration.
- **Per-tool review-candidate shape must agree across surfaces.** Review candidates for the same conceptual criterion ship across `scan_file.reviewCandidates[]`, `checklist.items[].candidates[]`, and `coverage.manualWithCandidates[]` — but the per-entry shape disagrees: `scan_file` ships `priority: null` / `confidence: null` while `checklist` populates both; `coverage` strips the `candidates: []` array entirely while `checklist` ships it populated; checklist candidates lack `findingId` / `groupKey` while scan_project findings carry both. An agent calling these surfaces in sequence (the canonical workflow) gets a different mental model of the same candidate at each call — the `priority: null` slot reads as "no priority assigned" when the same candidate on checklist had `priority: "high"`. The silent-miss failure mode is identical to the cross-surface count invariant but on the per-candidate field-shape axis. Closure: a single shared candidate-shape contract consumed by all three surfaces — same fields populated, same null-vs-omitted semantics, same identifier hash function. The candidate identifier (`findingId`) must be stable across surfaces so an agent can address the same candidate by id regardless of which tool it called.
- **Suppress-recommended is a distinct discriminator from guidance.** When `suggest_fix` ships `kind: "guidance"`, its primary advice should be a real fix direction the agent can pursue ("widen aria-label to contain the visible text", "promote the existing `<h2>` to `<h1>`"). When the rule's evidence model has conceded the criterion may not apply on this substrate and points the agent at the source-level disable pragma ("If this page is rendered inside a parent layout that supplies the title, suppress with `<!-- ra11y-disable wcag22:1.3.1 -->`"), the honest discriminator is `kind: "suppress-recommended"` — *not* `kind: "guidance"`. Conflating them under one kind makes the agent's branching dishonest: the agent reads `kind: "guidance"` and budgets for an actionable fix; if every guidance response could secretly be "I give up — please add a pragma," the agent has to inspect prose to tell them apart, the same parse-the-string failure mode "Ambiguous field shapes are dishonest" warns against. The discriminator partitions on a deterministic predicate (suggestion text mentions `ra11y-disable` or `suppress with`); the per-class plan tally mirrors via `plan.fixesByClass.suppressRecommended` so per-call shape and per-class headline agree (per "Per-call shape must agree with per-class plan tally"). The `suppress-recommended` lane partitions findings out of the lane the rule's `fixClass` would route into — `countFixesByClass` routes by suggestion-text predicate first, then by `fixClass`, so the lanes never double-count. Closure: when a rule's emission text on a given substrate is honestly "verify and dismiss with a pragma," the response shape names that — never sneak it through the actionable-guidance kind.
- **Bootstrap output must be paste-safe.** Bootstrap-class tools (`bootstrap`, `propose_config`, `suggest_*`) ship code or config the agent is expected to apply directly — paste into `ra11y.config.ts`, run as a script, write to a file. When such output is syntactically invalid (trailing commas in TS arrays, unterminated strings, mismatched brackets) OR semantically destructive (excludes that sweep authored-source subtrees, includes that pull in dependencies the user didn't ask for), the agent applying the output without a syntax pre-check breaks the user's project. The doctrine bullet "Don't duplicate capability the agent already has" warns against in-tool analysis the agent could redo with Read+Grep — but bootstrap tools by construction generate output the agent CANNOT redo cheaply (the predicate is the corpus-wide vendor classification). Therefore bootstrap output bears a higher correctness bar than ordinary tool output: it must parse as valid syntax in the target language by construction, and any classification predicate that gates inclusion/exclusion must err on the side of false-negative inclusion (do nothing) rather than false-positive exclusion (sweep authored source). The 2026-04-30 sweep observed `bootstrap.suggestedConfig.exclude` shipping with a trailing comma AND sweeping 100+ authored-source subdirectory globs as the worst-case regression. Closure: bootstrap output passes a syntax pre-check before serialization (TS / JSON / YAML lex pass); classification predicates default to do-nothing when evidence is ambiguous; integration test that the suggested config parses and that no `<authored-src-tree>/**` glob lands in `exclude` without an explicit vendor-classification signal.
- **Bootstrap-class lanes must equal project-rooted lanes.** The "Per-tool lane and warning-set classification must agree" rule names `scan_project` / `scan_file` / `checklist` / `coverage` as the surfaces whose lane labels must reconcile; bootstrap-class tools (`bootstrap`, `propose_config`, `suggest_*`) sit one rung downstream and consume the same scan output, so their headlines must reconcile too. Observed regression: `scan_project.plan.fixesByClass` enumerates 5 lanes (`mechanical`, `guidance`, `runtimeOnly`, `verifyInSource`, `suppressRecommended`) while `bootstrap.scan.fixesByClass` on identical cwd enumerates only the first 4 — the `suppressRecommended` lane silently disappears (343-finding gap on the corpus where it was first observed). Same shape on wrappers: `bootstrap.wrappers.candidates: []` while `detect_native_wrappers.opaqueCustomComponentNames.length: 14` on identical cwd. An agent reading the bootstrap headline gets a smaller mental model of the same scan than scan_project would have given; the gap is silent because both tools succeed. Closure: bootstrap, propose_config, and suggest_* consume the same shared lane / wrapper enumeration as the project-rooted tools — same lane keys, same wrapper candidate shape, same field set. Pin via integration test on identical cwd: every lane key in `scan_project.plan.fixesByClass` is present in `bootstrap.scan.fixesByClass`; every wrapper-candidate shape that ships from `detect_native_wrappers` is reachable from `bootstrap.wrappers.candidates`.

## Handling "reduce noise" feedback

When a field report suggests "reduce noise," ask first: noise for whom? If the answer is "a human reviewer," the answer is usually no — the agent is the consumer and it wants the signal. If the suggestion is "encode this spec exemption as a heuristic so the agent doesn't have to verify," the answer is also no — heuristic detection and spec carve-outs operate at different confidence levels, and the deterministic source-level disable is the correct mechanism. If the suggestion is "put the obvious-noise candidates in their own bucket so I can skip them," the answer is also no — see the asymmetry rule above. Enrich the `reason` text with the dismissal signal; keep the candidate in the primary list.
