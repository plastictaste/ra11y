# AI-first consumer model

ra11y's primary consumer is an AI agent calling the MCP tools — not a human reading a dashboard. CLI and formatters exist, but the design center is the agent. Several common tooling defaults invert under this assumption; treat the rules below as load-bearing when triaging field reports or designing new surfaces (MCP tools, response shapes, reports, formatters).

This doctrine lives here (rather than in CLAUDE.md) so it loads automatically when editing code that shapes MCP tool responses — `src/mcp/**`, `src/reports/**`, `src/output/**`, `src/review/**`, plus the authoritative shape-owning files `src/types/violation.ts`, `src/types/review.ts`, and `src/engine/scanner.ts` — via the path-scoped rule at `.claude/rules/mcp-response-shapes.md`. Outside those paths, the doctrine is still discoverable via this page and CLAUDE.md § 1.

## Rules

- **Surface, don't suppress.** Agents read every candidate in milliseconds; reviewer fatigue isn't the constraint a human-facing tool optimizes around. False positives a human would tune out are cheap for an agent to dismiss with one file read. Suppression discards signal the agent would use to triage. Default to surfacing with enough context for the agent to investigate.
- **Don't downgrade priority to hide things.** "Mark as low priority" is a UX lever for human attention budgets. Agents don't have one — they just sort. Surface honestly and let the agent rank by criterion + reason + context.
- **Verbose meta is signal, not clutter.** `configSource`, `activeNativeWrappers`, `rulesEvaluated`, per-extension file counts — these are scan-confidence telemetry the agent actively uses to decide whether the scan had teeth and what to call next. Don't trim them to look terse. (Note: `configSearchedFrom` is present-when-meaningful — omitted when it would just echo the caller's `cwd` or a `scanned.root` already in the response, per Q6 de-duplication of the config-context triple readout.)
- **Review *candidates*, not assertions.** For manual criteria, return locations + a short `reason` that frames the question. Don't try to be smart about "what the user really meant" — agents are better at that than heuristics.
- **One tool call should answer "what next?"** Each response carries `nextStep` hints, criterion IDs, and counts that match the other tools' counts. Cross-surface drift (`scan` says 21, `checklist` says 4) forces wasted round trips; invariants like the manual-review-count test exist to prevent this.
- **Default-exclude globs are suppression too.** Growing `DEFAULT_EXCLUDED_PATTERNS` in `src/input/discover.ts` to "reduce noise" from scans is the same mistake as downgrading severities or silencing finders — it just happens one level earlier in the pipeline. An agent can dismiss a finding whose path contains `test/fixtures/` or `stories/` in one read; it can't un-suppress a file that never got parsed. Only add an exclusion when findings in that path tree are *definitionally wrong for any consumer* (generated code, `.min.*`, vendor dumps). "Most people don't want to see this" is a human-attention argument, not a correctness one; it is not sufficient. If an existing entry in the list can't clear that bar, it's a bug, not a precedent.
- **No heuristic suppression, even for spec carve-outs.** WCAG's exemptions (logotypes, process-page exception, essential presentation) are conceptual rules — *detecting* whether a given element falls under one is a heuristic on weaker evidence than the agent has. An `<img>` with `alt="Acme logo"` might be a brand mark, or it might be a product shot the author mislabeled. A repo with three HTML files might be an SPA shell, or it might be the start of a content site. Our attribute-level snippet is not enough to make that call; the agent reading the whole file is. Encoding a heuristic as suppression replaces honest "please verify" with false confidence and risks silent false negatives on real violations. The deterministic escape hatch is the source-level disable pragma (`<!-- ra11y-disable wcag22:1.4.5 -->` / `{/* ra11y-disable wcag22:2.4.5 */}`) — once an agent investigates and dismisses, the pragma makes that dismissal durable. No guessing required. If a specific review candidate keeps drawing field-report complaints, the fix is better `reason` text (so the agent dismisses faster), not a finder-level carve-out.
- **Labeled buckets are suppression too.** "Splitting findings into a primary list and a deprioritized/verbose/likely-X bucket" is the move that looks like labeling but behaves like suppression — once consumers learn the bucket is skippable by default, the silent-miss failure mode is identical to hiding the finding outright. A bucket is only honest when its label is *provable from the code* (e.g. `likelyIrrelevant` for "no `<video>` elements in the scanned files" — a deterministic fact). Filename patterns, identifier patterns, and spec-exemption guesses do **not** earn a bucket. They earn reason-text enrichment, which the agent reads per-candidate and acts on individually. The test before adding a new bucket: would the label be correct 100% of the time from the evidence the scanner has? If it's a heuristic, the answer is no.
- **Failure modes are asymmetric; the rules above lean against the cheaper failure.** Over-surfacing → the agent dismisses in one read, at a few seconds' cost, and the judgment stays visible. Under-surfacing → a real violation never reaches the agent; the user doesn't know it happened; the miss is silent and non-reversible. When a reasonable-sounding field report asks for "less noise" in a way that would hide findings, remember the costs are lopsided — and that "this looks tractable, we can split the difference" is where the silent-miss regressions live. Durable rule: when in doubt, surface and annotate; never bucket-then-filter.
- **Numeric-threshold heuristics are suppression.** "Auto-dismiss when the setTimeout duration is ≤ 5 seconds," "only flag when the image is ≥ 100px wide," "require at least N call sites before reporting" — thresholds dressed up as precision checks are the same heuristic-suppression move as filename-pattern matching. The threshold picks a point on a continuous axis and hides everything on one side of it; the silent-miss failure mode is identical. A real session timeout of 4.5 seconds is indistinguishable from a debounce of 4.5 seconds from static analysis alone, and the agent reading the surrounding code is the only correct arbiter. Encode the duration/size/count in the `reason` text as additive context ("setTimeout with 2000ms literal"); let the agent decide.
- **Don't duplicate capability the agent already has.** Before adding in-tool analysis — cross-file identifier resolution, path walking, fuzzy name matching — ask whether the consuming agent can do the same thing with Read + Grep. If yes, the tool doing it risks being redundant at best and confidently wrong at worst: in-tool heuristics produce output the agent can't tell to mistrust ("`handleChange` defined at line 42, body is clean" is a liability the first time line 42 is a shadowed binding). The tool's job is to *point* — file, line, pattern; the agent's job is to *investigate*. This inverts the default for human-facing tools, where doing more in-process is usually better. Reflex check every time feedback asks for "smarter" analysis in a finder.
- **Interrogate the problem before accepting the solution's shape.** When feedback says "add a show_X tool" or "we need a Y flag," the first check is whether the capability already exists in a tool or call that wasn't discovered. Field reports carry the *problem* the reporter hit, not evidence of a structural gap. Accepting the solution's shape short-circuits that check and creates tool-bloat — more shapes on `tools/list`, more drift surface, more overlap — paid even when the underlying problem was documentation. If the capability exists but is hard to find, sharpen the tool description; if it doesn't, then design.
- **Ambiguous field shapes are dishonest.** A field that is sometimes populated and sometimes `""` (or `null` used as "unknown") forces the agent to re-read and disambiguate whether the value is unavailable or genuinely empty — and because agents usually treat the empty value as real data, the downstream mistake is silent. Omit the field entirely when it has no meaningful value; use conditional spreads at the response-assembly site (`...(x ? { field: x } : {})`). `newText: ""` under `kind: "edit"` is the canonical mistake; `snippet: ""` alongside a populated `sourceContext` is the same bug in another place. The test: if a downstream consumer has to ask "did I get an empty answer or no answer?", the shape has failed. This applies only to optional fields — schema-required fields stay populated; the shape signals "present-when-meaningful."
- **Zero-output success is ambiguous failure.** A response shaped like "success + 0 findings / 0 files scanned / empty list" is indistinguishable from "the input never reached the tool." The canonical case: `scan_project({ cwd: "/tmp/wrong-path" })` returns `{ filesScanned: 0, totalFindings: 0 }` with success — the agent concludes "clean codebase" when the reality is "tool never ran," and the miss is non-reversible once the agent acts on it. When the input or configuration is plausibly malformed — nonexistent `cwd`, zero parseable files, no config resolved, CSS absent but Tailwind classes detected, template files parsed as literal — emit a response-level `warnings: string[]` (structured codes preferred: `scanned_zero_files`, `root_source_defaulted`, `no_config_found`, `tailwind_detected_css_undercounted`, `template_files_parsed_as_literal`). The test: can a caller distinguish success-with-nothing-to-do from success-with-nothing-ran by reading the response alone? If not, the shape is dishonest. This is the response-level analogue of the per-field rule above.
- **Composite headline counts are dishonest.** A top-level counter like `manualReviewRequired: 21` or `fixSuggestionAvailable: 2` reads as "this much work to do," but often sums categorically different sub-buckets — grounded candidates with a file:line vs. bare-criterion prompts, mechanical edits vs. prose-only guidance. Agents budget against the headline, and the composite number inflates or misclassifies the work. If a top-level counter names one concept, it must count one kind of thing; when two kinds exist, split into two top-level counters (`actionableManualItems` + `untargetedCriteria`) so each names exactly what it measures. Do NOT keep the composite as a sibling next to the structured per-kind tally: two counters both framed as "how many of X" will disagree whenever they measure different slices, and the disagreement is silent (the agent reads one headline first and budgets against it). Canonical case: `plan.safeEditsAvailable: 14` shipped next to `plan.fixesByClass.mechanical: 266` — same response, same framing, an 18× disagreement that forced the agent to pick one. The fix was to drop the composite; the per-lane `fixesByClass` sibling already carried the honest signal, and callers that want an apply-now subset sum the two editable lanes (`mechanical + verifyInSource`) off the structured tally themselves. Labels on sub-fields aren't enough if a headline still sums them — the summary string consumers read first shouldn't need footnotes to be correct. Worked precedent: `plan.totalFindings` was removed (not renamed to `plan.totalFindingsComposite`) on 2026-04-24 once the same disagreement surfaced summing source vs. buildArtifact lanes — a renamed-but-retained composite still occupies the "first thing the agent reads" slot and the silent-miss failure mode is identical, so deletion is the durable answer rather than label-stretching.
- **Heuristic-mislabeled meta sub-fields are dishonest.** The labeled-buckets rule applies one level deeper than its canonical surface: any `reason`-shaped sub-field on a meta entry must clear the same "provable from the code" bar as the bucket itself. A field like `scannedBuildArtifacts[].reason: "minified"` reads to the agent as a deterministic classification — but if the predicate is a single-long-line heuristic that fires on hand-authored long-line files (template-literal islands inside JSX-flavored sources, prop-bundle wrappers, SCSS function bodies with long type signatures), the label lies and the agent's downstream triage (skip the file, suppress findings, re-route fixes) propagates the lie silently. The same applies to `templateDirectivesFound: ["handlebars-or-mustache"]` when the evidence is `${{ ... }}` GitHub-Actions expressions in `.yml` files, and to any future `reason: "<token>"` sub-field added to a meta array. Test before adding such a field: would the token be correct 100% of the time from the evidence the scanner has? If the answer is "usually," drop the deterministic-sounding token and surface the underlying signal (line-length distribution, sourcemap-sibling presence, hashed-filename pattern, directive-token co-occurrence) as additive evidence the agent can read without the label. Recurring 2026-04-24 sweep finding across multiple codebases — the silent miss is the agent treating mis-labeled vendor as actually-vendor and rerouting fix suggestions away from a file the user did author.
- **Heuristic emission is the symmetric twin of heuristic suppression.** The "no heuristic suppression" rule has a mirror: a rule that *emits* on speculation about composition or rendering — "When composed into a layout, will likely sit alongside another `<form>`", "the value `p` might be a session timeout", "this anchor probably toggles a sibling carousel" — is the same predicate-strength mistake in the opposite direction. Encoding low-confidence evidence as a deterministic finding (severity `error`/`warning`) leaks the heuristic's uncertainty into a slot the agent reads as "this is real." Agents budget against severity; a speculative rule fire wastes that budget the same way speculative suppression hides a real one. Test before emitting: is the predicate provable from the code in this file alone, or does it depend on guessed composition? If the latter, the finding belongs on the review-candidate surface (where `reason` text frames a question the agent verifies), not on the rule surface. Canonical case: `semantics/duplicate-landmark-unlabeled` emitting on a single unlabeled `<form>` because "it likely sits alongside another form once composed" — the composition is unobservable; the emission is dishonest. Closure path: gate the emission on confirmed sibling evidence in-file, or move the predicate to a finder.
- **Reason text and severity must agree.** When a rule's `reason` text concedes the predicate it claims to violate is satisfied — "the visible text already carries the status word", "the parent `<a>` already carries the accessible name", "if standalone single-page this criterion may not apply" — the rule must not still emit at `error`/`warning` severity. A `reason` that contradicts its own severity is a dishonest shape: the agent budgets against the severity, reads the reason, and discovers the budget was wasted; worse, the contradiction trains the agent to mistrust the rule even on the cases where it's right. Three closure paths: (a) suppress emission on the conceding branch; (b) downgrade to a review candidate so the framing matches "please verify"; (c) rewrite the reason to surface what is *actually* still in question (e.g. "color may still be the *sole* cue for users who can't read the keyword"). Recurring 2026-04-24 sweep finding — `color/meaning-by-color-only` emitting at `error` on `<button class="btn-danger">Danger</button>` while the reason concedes the word "Danger" is present is the canonical case; same shape recurs across 2.4.5 candidates, tooltip rules, and any predicate whose self-narration doubles back on itself. The 2026-04-25 second-pass sweep extends this rule to *conceded uncertainty* in addition to conceded satisfaction: a `reason` that hedges with `"verify the inheritance chain"` / `"runtime behavior may differ"` / `couldBeWrongBecause: [...]` while severity stays `error`/`warning` is the same shape — the framing concedes the predicate may not hold, the severity claims it does. Same three closure paths apply.
- **Cross-surface count invariant.** When the same conceptual counter ships from two project-rooted tools on the same input — `actionableManualItems` from `scan_project.plan` vs `checklist.summary.actionable` vs `coverage.manualWithCandidates.length`; `untargetedCriteria` from all three; `parseErrorFileCount` from `scan_project` vs `coverage` — the values must agree. Drift is silent: the agent reads the first headline, budgets against it, and notices the disagreement only by chance when calling the next tool the response itself recommends. The 2026-04-25 second-pass sweep observed every named counter drifting on every cwd (10/7/7, 6/5/5, 12/9 actionable; 14/13/13 and 17/15/15 untargeted; 546 vs 538 parse-errors). Each shared counter must be computed once in a shared helper consumed by all surfaces; an integration test pins equality on identical cwd. The same applies to fields named like `countsBySurface` — a field whose name implies cross-surface reconciliation must actually reconcile, not multiply (a 4-way internal spread within one response is the worst-case shape). The 2026-04-25 evening fourth-pass sweep extends this rule to *scan-confidence warning telemetry*: when scope-level warnings like `scanned_build_artifacts_present` / `scanned_minified_file` / `bulk_catalog_detected` ship on `scan_project` but are silently absent from `checklist` / `coverage` on the identical cwd, an agent that calls `checklist` first on a bulk-vendor corpus has zero signal that 996 minified files exist. Warnings whose evidence is the corpus (not the rule fan-out) must reach every consumer of that corpus; the silent-miss failure mode is identical to the count-disagreement case. Closure: every project-rooted tool emits the same scope-level warning set on identical cwd, computed once in the shared scan-confidence helper.
- **Parser-failure invalidates per-file confidence.** When a file appears in `analysisCoverage.parseErrorFiles[]` or `partialParseFiles[]`, every `perRuleCoverage` entry crediting that file must downgrade `coverageConfidence` to `"low"` / `"medium"` with a `reason` naming the parse failure (`"parse_failed"` / `"partial_parse"`). A `confidence: "high"` entry on a file the parser bailed on is the parser-side mirror of "reason text and severity must agree" — the per-rule label claims the rule observed full evidence; the recorded parse error says it didn't. Agents reading per-rule coverage as scan-confidence telemetry are silently misled. Same invariant applies to `fragmentFiles[]`: when a file is classified as a fragment (`_includes/`, `_partials/`, README.md residue), document-shaped rules (`landmark-main`, `heading-hierarchy`, `page-titled`, `lang-attribute`) must downgrade with `reason: "fragment_input_no_document_envelope"` rather than reporting `"high"` confidence that they could not honestly establish. The general rule: any classification that gates the rule's evidence model must propagate to that rule's confidence label in the same response.
- **Oversize-success is ambiguous failure.** A response that succeeds internally but whose serialized payload exceeds the MCP host token cap leaves the agent with only a host-level transport error — no `plan`, no `meta`, no `warnings`, no `nextStep`. The silent-miss failure mode is identical to zero-output-success: "the tool ran on nothing" and "the tool ran fine but its envelope evaporated" are indistinguishable from the agent's seat. The 2026-04-25 second-pass sweep observed bulk-corpus scans producing post-clip payloads still 18× over the host cap. The tool's own internal mitigation (clip files, set `truncated: true`, add `response_token_budget_truncated`) is too late if the post-clip envelope is still over budget. When pre-serialization size estimation crosses a sentinel (e.g. 24KB), fall back to a minimum-honest envelope: keep `plan` + `meta` + `warnings: ["response_dropped_files_oversize"]` + `nextStep` (recommending scope-down), drop `files[]` rather than the whole response. The agent can still route once on what arrived; without the envelope, it cannot.
- **Routing skips that drop content are the symmetric twin of suppression.** Routing `.js` through the tsx parser silently drops every plain-JS file's potential findings (the parser bails on relational expressions read as JSX); failing to recurse into `innerHTML` / `insertAdjacentHTML` / `document.write` template-literal HTML islands inside `.js` files silently drops every dynamically-injected widget's potential findings; rejecting `.xhtml` / `.mkdn` / `.erb` as `file-unsupported` while accepting `.html` / `.markdown` silently drops valid input. The agent cannot un-skip a file the scanner refused to parse. Apply the same scrutiny to routing decisions as to suppression: when a file-shape the parser declines to handle could plausibly contain real findings, emit a structured warning (`text_source_skipped`, `binary_assets_skipped`, `js_innerhtml_template_literal_unparsed`, `parser_bailed_on_non_jsx_in_tsx_route`) so the agent can decide whether to re-route or scope around it. The two skipped-extension warnings are split by predicate so the actionable text-source subset doesn't get buried under binary-asset volume on bulk catalogs (a `.jpg: 1835` topExtension hiding `.php: 30` is the canonical regression closed by the split). Symmetric to "no heuristic suppression": under-parsing is the same silent-miss failure mode as under-emitting; both warrant explicit telemetry so the agent can do its own triage.
- **Per-finding confidence must reflect per-rule coverage limitations.** When `perRuleCoverage[ruleId].coverageConfidence` is `"medium"` / `"low"` with a documented limitation reason (`cross_file_listener_resolution_not_attempted_by_rule`, `cross_file_idref_resolution_not_attempted_by_rule`, `cross_file_custom_property_resolution_not_attempted_by_rule`), every per-finding emission from that same rule in the same response must propagate the limitation — either by downgrading per-finding `confidence` to match the per-rule label or by echoing the limitation reason as additive context on each finding. The 2026-04-25 third-pass sweep observed `keyboard/handler-missing` reporting per-rule `coverageConfidence: medium` with the cross-file-listener limitation code while emitting per-finding entries at `confidence: high, severity: error` against native `<button>` elements wired up by sibling `.js` (≥25 hits in one scan; recurring across 2 corpora). The agent reading per-rule coverage gets one signal ("this rule is limited on this corpus"); the same agent reading per-finding confidence gets the opposite ("each of these is high-confidence"). Same rule, same response, contradictory claims — same shape as "reason text and severity must agree" but at a different layer of the response. Closure: when per-rule confidence is degraded with a documented reason, propagate the degradation to per-finding `confidence` OR include the reason in each finding's `couldBeWrongBecause`.
- **Reason-token suffixes must name the actual predicate, not an input-specific hiccup.** A `reason` code suffixed `_limited_on_this_input` reads to the agent as "we tried this input and were limited" — implying that a different input might resolve the limitation. When the underlying rule has `crossFileCapable: false`, the rule's design declares it does not attempt cross-file resolution at all; the limitation is a permanent rule-design choice, not an input-specific hiccup. Encoding the rule-design limitation as input-specific framing risks the agent inferring "maybe a different input would resolve it" and wasting a re-scan. The honest suffix is `_not_attempted_by_rule` for case (a) — the rule structurally never attempts. Reserve `_limited_on_this_input` for case (b) — a rule that does attempt cross-file resolution but was bounded by an incomplete input (partial-parse, file-set-limited). Test before adding such a suffix: does the rule's design actually try the resolution this code names? If not, the `_limited_on_this_input` framing lies. Recurring 2026-04-27 sweep finding — the canonical case was the cross-file-listener limitation code emitted from rules tagged `crossFileCapable: false` while suffixed `_limited_on_this_input`; closure renamed both the predicate-strength-gated and the project-scoped variants to `_not_attempted_by_rule` so the suffix matches the predicate.
- **NextStep prioritization on truncated/bulk responses must avoid first-by-filename routing.** `nextStep` / `nextStepStructured` defaults to picking the alphabetically-first finding when the response is truncated or the corpus is bulk-vendor-heavy. The 2026-04-25 third-pass sweep observed routing the agent to a visual-regression fixture file (on a CSS-framework corpus), an underscore-prefixed scaffold-directory `index.html` (on a vanilla-JS exercise corpus), and a vendor stylesheet path already classified as `scannedBuildArtifacts` (on a bulk-template corpus). The agent following `nextStep` wastes a `suggest_fix` call on non-actionable input — a vendor file the user can't edit, a fixture file with no rendered consumer, or a scaffold dir with placeholder content. Per the existing "one tool call should answer 'what next?'" rule, the canonical first-call recommendation must reflect impact, not lexical order. Closure: when `truncated: true` OR when the candidate file is in `scannedBuildArtifacts`, route `nextStep` to the highest-firing rule's first non-vendor finding, OR to a "scope down via `additionalPaths`" structured suggestion. Recurring across 3 corpora.
- **Truncated containers must rename or sentinel, not retain.** When a top-level container field (`meta`, `analysisCoverage`, `scannedBuildArtifacts`, `perRuleCoverage`) is gutted by a truncation pass, retaining the field name while stripping the substantive sub-fields is dishonest in the same way as ambiguous-empty-string. The agent reads `meta` and finds 9 trivial scalars; it cannot distinguish "this codebase has no scan-confidence concerns to surface" from "the meta block was clipped to fit the envelope." The silent-miss failure mode is identical to zero-output success: success-with-nothing-to-narrate and success-with-narration-discarded look the same from the agent's seat. The 2026-04-26 multi-corpus sweep observed this on `meta` (9 keys remained, 10+ stripped under `response_meta_truncated`) and on `coverage.perRuleCoverage[]` (empty array under truncation while `scan_file` on the same input ships ~95 rows). Closure paths: (a) rename the surviving field on truncation (`metaTruncated`, `perRuleCoverageTruncated`); (b) replace each absent sub-field with a `{truncated: true, reason: "..."}` sentinel; (c) pair with `warningsDetails.<warning>.fieldsDropped: ["analysisCoverage", "scannedBuildArtifacts", ...]` so absence is visible from the warning channel. The general rule: a container field whose contents may be silently discarded must signal the discard at the field level — name retention without sentinel is the worst-case shape because it looks like a populated container.
- **Per-call shape must agree with per-class plan tally.** When `plan.fixesByClass.mechanical: N` advertises N findings as having a safe edit available, every `suggest_fix(ruleId, file, line)` call that resolves to one of those N findings must return `kind: "edit"` with materialized `oldText`/`newText`. The earlier `meta.mechanicalInPrinciple: true` annotation on `kind: "guidance"` responses was itself the contradiction this rule warns against — two sibling fields under the same response answered "is a mechanical edit available" with opposite values, and the agent that read the plan tally first budgeted against a fixable count the per-call surface wouldn't honor. The 2026-04-26 sweep observed the contradiction across 4 corpora on rules including `document/lang-attribute`, `forms/labels-required`, `aria/icon-child-missing-aria-hidden`, `semantics/section-accessible-name-missing`, `color/meaning-by-color-only`, and `semantics/landmark-main`; closure path (a) below has since been applied — the field is removed entirely and the affected rules carry `fixClass: "verify-in-source"`. Closure paths: (a) when `kind: "guidance"` is the honest per-call shape because the static evidence cannot produce an edit, deduct from `plan.fixesByClass.mechanical` (re-tag the rule's `fixClass` from `mechanical` to `verify-in-source`); cross-surface honesty then flows through `plan.fixesByClass` alone (mechanical / verifyInSource counted as separate lanes), and callers wanting the apply-now subset sum `mechanical + verifyInSource` off the structured tally; (b) when the rule genuinely emits a deterministic edit, the per-call response must materialize `kind: "edit"`. Integration test: for every rule contributing to `plan.fixesByClass.mechanical` on a given response, calling `suggest_fix` on at least one such finding must return `kind: "edit"` (locked in by `tests/integration/suggest-fix-plan-tally-parity.test.ts`). This bullet is the per-call analogue of "Composite headline counts are dishonest" — the headline counter and the per-call shape must agree, not just the headline and a sibling tally.
- **Reason / priority / fix-description must agree across all three channels.** The existing "Reason text and severity must agree" rule extends to two more channels in the response: review-candidate `priority` (parallel to severity for the manual-review surface) and per-finding `fix.description` text (parallel to `reason` for the suggest-fix lane). A candidate at `priority: "high"` whose reason concedes "if this is a standalone single-page file or SPA, the criterion may not apply" is the candidate-priority analogue of the conceded-uncertainty severity case. A finding at `severity: "error"` whose `fix.description` literally instructs "Cross-file check: grep the selector in your HTML to confirm the target isn't already a `<button>` or `<a href>`" is the fix-description analogue — the description channel concedes the predicate may not hold while the severity claims it does. The 2026-04-26 sweep observed both shapes recurring (wcag22:2.4.5 candidates at `priority: "high"` with SPA-may-not-apply concession; `keyboard/handler-missing` at `severity: "error"` with grep-the-html fix description). Closure paths: parse reason/description text for hedging tokens (`may not apply`, `only if`, `verify…before`, `Cross-file check: grep`, `confirm…isn't`) and either (a) downgrade the corresponding attention-budget signal (severity → warning, priority → medium/low), (b) move to a review candidate so framing matches "please verify," or (c) perform the cross-file/cross-context check the description prescribes when the scanner already has the evidence (the `keyboard/handler-missing` HTML AST case is the canonical "the scanner could have done this" instance). The general rule: every channel an agent reads for attention-budgeting (severity, priority, confidence, fix.description-imperative-verbs) must agree with the reason text it ships alongside.
- **Empty `warningsDetails.<code>: {}` is dishonest.** A warning code declared in `warnings[]` whose corresponding `warningsDetails.<code>` ships as the empty object `{}` denies the agent any way to triage what the warning measures — which files, how many, what predicate. The empty-object payload is the warning-channel sibling of the ambiguous-empty-string per-field rule and the truncated-container name-retention rule: an agent reading the warning name infers "this warning fired with specifics I can act on" but the specifics are absent, and the silent-miss failure mode is identical (the agent budgets against a warning whose payload is unactionable). The multi-corpus sweep observed this on `parser_bailed_on_non_jsx_in_tsx_route` and `parser_bailed_zero_findings` shipping `{}` payloads on multiple corpora, denying the agent any per-file file-list to scope around. Closure paths: (a) populate the details payload (file list, count, evidence, reason) at emit time; (b) omit the warning code from `warnings[]` entirely if there's nothing actionable to ship; (c) consolidate with an existing more-specific warning code that already carries a payload. Never ship the code with an empty payload — the warning channel is for the agent to act on, not to acknowledge.
- **Per-tool lane and warning-set classification must agree.** When the same file or cwd is observed by `scan_project`, `scan_file`, `checklist`, and `coverage`, the lane classification (`scanKind: "source" | "buildArtifact"`), warning-set, and minimum-honest-envelope behavior must agree across all four. The cross-surface count invariant covers numeric drift; this bullet covers structural drift: a file that `scan_project` classifies under `scannedBuildArtifacts` ships as `source`-lane findings when the agent calls `scan_file` on the same path; corpus-level scan-confidence warnings (`bulk_catalog_detected`, `response_dropped_files_oversize`, `response_token_budget_truncated`, `truncated_files_dropped`, `text_source_skipped`, `binary_assets_skipped`, `js_innerhtml_template_literal_unparsed`) ship from `scan_project` but silently absent from `checklist`/`coverage` on identical cwd; the minimum-honest envelope (drop `files[]`, keep `plan` + `meta` + `warnings` + `nextStep`) implemented at `scan_project` is absent at `checklist` and `coverage`, so an oversize bulk-vendor scan succeeds at the project surface and transport-fails at the manual-review surface. An agent that calls `checklist` first on a bulk corpus, or `scan_file` directly on a vendor stylesheet, gets a different mental model of the same input than `scan_project` would have given. The multi-corpus sweep observed all three drifts simultaneously on bulk-vendor corpora (lane disagreement on minified vendor css; 4 corpus-level warnings absent from checklist+coverage; oversize transport-failure on checklist+coverage with no envelope fallback). Closure: a single shared scope-classifier helper consumed by all four project-rooted/file-rooted tools — same lane labels, same warning set, same envelope ceiling, same fallback — pinned by an integration test on identical cwd.

## Handling "reduce noise" feedback

When a field report suggests "reduce noise," ask first: noise for whom? If the answer is "a human reviewer," the answer is usually no — the agent is the consumer and it wants the signal. If the suggestion is "encode this spec exemption as a heuristic so the agent doesn't have to verify," the answer is also no — heuristic detection and spec carve-outs operate at different confidence levels, and the deterministic source-level disable is the correct mechanism. If the suggestion is "put the obvious-noise candidates in their own bucket so I can skip them," the answer is also no — see the asymmetry rule above. Enrich the `reason` text with the dismissal signal; keep the candidate in the primary list.
