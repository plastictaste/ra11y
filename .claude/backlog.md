## Track Q19 — Multi-corpus AI-first sweep (2026-05-07)

Fourth multi-corpus AI-first sweep on four shape-distinct corpora (a vendor-heavy CSS framework with SCSS + JS sources; a Ruby static-site generator with mixed template directives; a tutorial-style HTML/CSS/JS collection of standalone lesson folders; a bulk HTML template catalog with vendor-heavy admin theme). 5 angles per corpus (scan_project / checklist / coverage / suggest_fix / bootstrap+detect_native_wrappers) returning structured JSON. ~93 raw findings → 12 actionable after dedupe against open Q16 + Q17 items (the bulk of repeat findings — empty warningsDetails payloads on present-when-meaningful BinaryPresenceMarker codes, cross-surface meta drift, truncation reporter overlap, per-finding fixClass-vs-kind drift, severity-vs-conceded-uncertainty — confirmed reproduction on all four corpora and remain captured under the existing open items).

- [ ] **Q19-KIND-ENUM-MISSING-VERIFYINSOURCE-RUNTIMEONLY** `plan.fixesByClass` enumerates 5 lanes (`mechanical`, `guidance`, `runtimeOnly`, `verifyInSource`, `suppressRecommended`); per-call `suggest_fix.kind` enum admits 4 values (`edit`, `guidance`, `suppress-recommended`, `none`). Reproduces on 3 of 4 corpora. The `verifyInSource` and `runtimeOnly` plan-lane findings collapse into per-call `kind: "guidance"` (canonical case: a vendor-heavy admin catalog with `verifyInSource: 1581` source findings — every sample returned `kind: "guidance"`); an agent budgeting against the 5-lane plan tally cannot reconstruct which `kind: "guidance"` returns came from which lane. Closure: extend the suggest_fix kind discriminator to mirror plan.fixesByClass (5 values: `edit`, `guidance`, `runtime-only`, `verify-in-source`, `suppress-recommended`), OR fold `verifyInSource` and `runtimeOnly` into `guidance` in plan.fixesByClass so the per-call surface and headline tally use the same vocabulary. Pin via integration test: every key in plan.fixesByClass has at least one matching per-call kind value across the rule registry. Per AI-first doctrine "Per-call shape must agree with per-class plan tally."
- [ ] **Q19-GUIDANCE-BOILERPLATE-SUPPRESS-PRAGMA** Every `suggest_fix` response with `kind: "guidance"` ships a standard `alternatives[].approach: "Dismiss in source via suppression pragma"` paired with explanation `"...paste <!-- ra11y-disable wcag22:1.3.1 --> above the cited element to make the dismissal durable..."`, regardless of whether the rule's evidence model honestly concedes the criterion may not apply on this substrate. The `suppress-recommended` discriminator already exists as a sibling kind, but bolting the pragma alternative onto every guidance response indiscriminately means agents cannot tell whether the pragma is the honest closure path or boilerplate template — the same ambiguity the kind discriminator was added to resolve. Closure: drop the boilerplate suppression-pragma alternative from `kind: "guidance"` responses; emit it only when the rule's evidence model concedes the criterion may not apply, in which case the response promotes to `kind: "suppress-recommended"` (the canonical sibling discriminator already wired through `plan.fixesByClass.suppressRecommended` and `countFixesByClass`). Per AI-first doctrine "Suppress-recommended is a distinct discriminator from guidance."
- [ ] **Q19-AUDIO-VIDEO-CONTROLS-HEDGED-DESCRIPTION** `media/audio-video-no-controls` ships at `severity: "error"` with `fix.description` that hedges `"If a custom JS-driven control bar is wired up to this element, keep \`controls\` as a fallback for when the script fails — or suppress this finding... once you have verified the custom controls expose play/pause and volume to the keyboard."` Description concedes the predicate may not hold (custom controls may already expose keyboard ops) while severity stays at error. Reproduces on a vendor-heavy CSS framework (21 findings on dist HTML demos) and a tutorial-style JS collection (21 findings on lesson index files). Closure: downgrade severity to `warning` when the rule emits `kind: "suppress-recommended"` with hedging description, OR perform the cross-file JS check the description requests (look for `play()` / `pause()` / `addEventListener` on the element's `id`) so severity stays at error only when truly violated. Per AI-first doctrine "Reason / priority / fix-description must agree across all three channels."
- [ ] **Q19-AUDIO-CONTROLS-TRANSCRIPT-HEDGED-DESCRIPTION** `media/audio-controls-or-transcript-missing` ships at `severity: "error"` with `fix.description` that hedges `"If the audio is purely decorative or supplemental and a text alternative already exists in the surrounding prose, suppress... once you have verified the in-prose alternative is equivalent."` Reproduces on a vendor-heavy CSS framework and a tutorial-style JS collection. Description concedes the predicate may already be satisfied via in-prose text alternative (which the static scanner can't see in one pass) while severity stays at error. Closure: downgrade severity to `warning` when fix.description concedes "an in-prose alternative may already exist," OR move emission to a review candidate so framing matches "please verify." Per AI-first doctrine "Reason / priority / fix-description must agree across all three channels."
- [ ] **Q19-FINDINGID-COLLISION-ACROSS-CRITERIA** A single `findingId` value addresses two distinct `(criterion, file:line)` tuples in the same checklist response. Reproduces on 2 corpora: on a Ruby SSG (29 candidates ship across `items[]` but only 27 unique `findingId` values — 2 collisions); on a tutorial-style JS collection (`findingId: 5f5cd980ba33` appears under both `wcag22:1.2.3` and `wcag22:1.2.5` items at the same `file:line`). Per the doctrine bullet `Per-finding identifiers must be addressable, not collision-prone`, calling `suggest_fix(findingId)` or applying a source-level disable pragma resolves ambiguously when one id maps to multiple items. Closure: include the criterion in the `findingId` hash input `(rule, file, line, column, criterion)` so each `(criterion, emission)` tuple gets a distinct id, OR rename the cross-criterion shared id to `findingGroupId` and ship per-`(criterion, emission)` `findingId` alongside. Pin via integration test: every `findingId` in a checklist response is unique. Per AI-first doctrine "Per-finding identifiers must be addressable, not collision-prone."
- [ ] **Q19-CHECKLIST-ITEMS-OMIT-CRITERIONID-GROUPKEY** `checklist.items[]` expose only `title`/`level`/`principle`; `criterionId` (e.g. `wcag22:2.5.1`) and per-candidate `groupKey` ship null on every item. `scan_project` candidates carry both. Reproduces on a tutorial-style JS collection and a bulk admin template catalog. Cross-surface address-by-id join is broken — agents reading checklist must title-match strings (lossy, language-dependent) against scan_project criteria rather than join by criterion id. Closure: populate `criterionId` on every checklist item alongside `title` (the field already exists on scan_project candidates so the contract is one-side-empty rather than schema gap); populate `groupKey` per-candidate matching scan_project's groupKey hash, OR omit via conditional spread when not meaningful — but never ship null. Pin via integration test: cross-surface review-candidate shape contract enforces `criterionId` populated on checklist items + `groupKey` populated or absent (never null). Per AI-first doctrine "Per-tool review-candidate shape must agree across surfaces."
- [ ] **Q19-BOOTSTRAP-NEXTSTEP-ECHOES-TRUNCATING-CALL** `bootstrap.nextStepStructured = {tool: "scan_project", args: {}}` on responses that themselves carry `response_token_budget_truncated` + `truncated_files_dropped` warnings. Reproduces on all four sweep corpora. The recommendation re-calls `scan_project` with empty args, the same scope that just produced the truncation, rather than narrowing via `restrictToPaths` / `additionalPaths`. Bootstrap has knowledge that the underlying scan truncated (it embedded the scan output and ships those warnings) but its own `nextStepStructured` doesn't propagate the scope-down recommendation that the embedded `scan_project` already correctly identifies. Closure: when `bootstrap.scan` carries `response_token_budget_truncated` / `truncated_files_dropped` / `bulk_catalog_detected`, route `bootstrap.nextStepStructured` to `scan_project({restrictToPaths: [<dominant non-vendor subtree>]})` propagated from the embedded scan's own `nextStepStructured`, OR to `summaryOnly: true`. Never echo `args: {}` that just produced the truncation. Pin via integration test on a bulk-vendor fixture: `bootstrap.nextStepStructured.args` is non-empty when truncation warnings are present. Per AI-first doctrine "NextStep handoffs must terminate at a narrowing tool."
- [ ] **Q19-ASTRO-ISLANDS-NO-PERRULE-CONFIDENCE-DOWNGRADE** `astro_islands_unrendered` warning fires on `.astro` files (49 files / 40% of corpus on a vendor-heavy admin template catalog; 103 files on a vendor-heavy CSS framework's docs site) but per-rule `coverageConfidence` doesn't downgrade for rules whose evidence on those files is structurally missing (the rendered output is unobserved). Document-shaped rules (`landmark-main`, `page-titled`, `lang-attribute`, `heading-hierarchy`) and event-handler rules (`keyboard/handler-missing`) emit at full confidence on `.astro` files where the static scanner sees only the frontmatter `<script>` island, not the rendered HTML. Per the doctrine bullet, any classification that gates the rule's evidence model must propagate to that rule's confidence label in the same response. Closure: when a file is classified `astro_islands_unrendered`, every per-rule entry crediting that file must downgrade `coverageConfidence` to `"medium"` / `"low"` with a `reason` naming the unrendered evidence (`reason: "astro_islands_unrendered_static_only"`); per-finding emissions on those files must propagate the limitation (move to review candidates or downgrade `confidence` AND `severity`). Per AI-first doctrine "Parser-failure invalidates per-file confidence" extended to template-island parse-as-literal classifications.
- [ ] **Q19-DUPLICATE-ID-ON-STANDALONE-SVG-FRAGMENT** `parsing/duplicate-id` ships at `confidence: "high"` `severity: "error"` with 37 emissions on standalone SVG files classified `analysisCoverage.fragmentFiles[].kind: "svg_standalone"` (canonical case: `dirt.svg`, `mole.svg` on a tutorial corpus's WhackAMole lesson). Standalone SVGs commonly use repeated path `id` values across separate `<symbol>` / `<g>` trees, where each tree is a structurally independent reuse target — the duplicate-id predicate is unreliable on standalone SVG and the rule fires on what is the SVG-native pattern. Closure: when `analysisCoverage.fragmentFiles[]` classifies a file as `svg_standalone`, propagate `fragment_input_no_document_envelope` to per-finding confidence on rules that fire on it (`parsing/duplicate-id`, `semantics/svg-title-missing`); downgrade severity to `info` or move to review candidates so the agent budgets correctly. Per AI-first doctrine "Parser-failure invalidates per-file confidence" extended to fragment classifications.
- [ ] **Q19-SCAN-FILE-LANE-DRIFT-FROM-SCAN-PROJECT** `scan_file` and `scan_project` classify the same vendor file under contradictory lanes on identical input. Canonical case on a vendor-heavy admin template catalog: `scan_project` on the cwd ships `meta.scannedBuildArtifacts.classified[]` listing `adminlte.css` as `definite-vendor-distribution` with findings counted in `plan.fixesByClass.guidance.buildArtifact: 112`; `scan_file` on the same path ships those findings under `plan.fixesByClass.guidance.source: 28, .buildArtifact: 0` — the same file's lane label flips from buildArtifact to source between project-rooted and file-rooted surfaces. An agent calling `scan_file` first on a vendor stylesheet has no signal that the file is vendor (which scan_project would have given). Closure: route `scan_file`'s lane classification through the same shared scope-classifier helper that `scan_project` uses (vendor-distribution / min-infix predicates), so a vendor stylesheet stays buildArtifact-tagged regardless of which tool the agent called. Pin via integration test on identical input: `scanKind` agrees across `scan_project.files[].scanKind` and `scan_file.scanKind` for the same path. Per AI-first doctrine "Per-tool lane and warning-set classification must agree."
- [ ] **Q19-COVERAGE-SCALAR-TWINS-FOUR-PAIRS** Coverage payload ships four scalar pairs that name the same concept twice in two locations: `manualCandidateEmissionsTotal` (top-level) = `summary.actionable.emissionsTotal` (nested); `automatedCriteriaPassRate` (top-level) = `summary.automatedCoverage.automatedCriteriaPassRate` (nested); `untargetedCriteriaForProject` (top-level) = `summary.untargetedCriteriaForProject` (nested); `scanned.{mode,root}` (top-level) = `meta.scanned.{mode,root}` (nested). Reproduces on a tutorial-style JS collection and a bulk admin template catalog. Each scalar pair ships an identical number in both slots, forcing the agent to reconcile silently which is canonical — the cross-field-redundancy axis the sibling-fields rule names. Closure: pick one canonical location per concept (preferred: keep the `summary.*` nested scalars; remove the top-level twins); or rename when the two slots genuinely measure different slices (none of these four pairs do). Pin via integration test: enumerate the four conceptual counters and assert each appears at exactly one location in the coverage response. Per AI-first doctrine "Sibling fields naming the same concept must use one shape."
