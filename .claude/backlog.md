## Track Q16 — Multi-corpus AI-first sweep (2026-05-05)

Second multi-corpus AI-first sweep on four shape-distinct corpora (CSS-framework distribution with documentation site; static-site-generator with mixed Liquid/ERB templates; vanilla-stack catalog of ~50 sibling demo subdirectories; vendor-template bulk catalog of ~100 sibling subdirectories with extensive duplicated vendor JS/CSS). 54 raw findings → 22 after cross-corpus dedupe → 18 actionable after filtering against existing Track Q15 items.

- [ ] **Q16-SCOPE-WARNING-SET-DRIFTS-ACROSS-PROJECT-ROOTED-SURFACES** Corpus-level scope warnings ship from scan_project but vanish on sibling project-rooted tools (checklist / coverage / propose_config) on identical cwd — observed across 3 of 4 corpora. Codes that drift: `truncated_files_dropped`, `response_token_budget_truncated`, `bulk_catalog_detected`, `js_innerhtml_template_literal_unparsed`, `dynamic_content_container_detected`, `linked_stylesheet_external_cdn_skipped`, `scanned_build_artifacts_present`, `source_language_unsupported`, plus dynamic warning payloads like `jsx_code_demo_prop_parsed_as_live_dom`. propose_config ships zero warnings/warningsDetails on a corpus where scan_project flagged 9 distinct concerns. An agent calling checklist or propose_config first has no scope-confidence telemetry that bulk-vendor or template-island conditions exist. Closure: single shared scan-confidence helper consumed by every project-rooted tool (scan_project, checklist, coverage, propose_config, bootstrap). On identical cwd the helper emits the same scope-level warning set across all four; surface-specific truncation codes are the only legitimate divergence. Add an integration test pinning `set(scan_project.warnings) - {surface-specific truncation codes} ⊆ checklist.warnings ∩ coverage.warnings ∩ propose_config.warnings`. Per AI-first doctrine "Per-tool lane and warning-set classification must agree" + "Cross-surface count invariant" — extension to scan-confidence telemetry.
- [ ] **Q16-TRUNCATION-REPORTER-CODE-DRIFT-AND-OVERLAP** Truncation events fire through different codes per surface and overlap within one response — observed across all 4 corpora. Two distinct shape problems: (a) per-surface code drift — scan_project uses `response_token_budget_truncated` + `truncated_files_dropped`, checklist uses `results_truncated_use_nextcursor`, coverage uses `response_dropped_files_oversize`. Identical conceptual event, three distinct names. (b) within-one-response overlap — `response_meta_truncated.fields` and `response_dropped_files_oversize.metaFieldsDropped` both enumerate dropped meta fields with non-aligned counts (e.g. 2 vs 12 entries, partial overlap on `analysisCoverage` / `scannedBuildArtifacts`). Plus per-warning inline `shownCount`/`totalCount` pairs duplicated by `response_dropped_files_oversize.slimTruncations`. Three reporters describing one truncation pass with no canonical channel. Subsumes per-surface name-retention regressions: empty `checklist.items: []` / `coverage.manualWithCandidates: []` under truncation indistinguishable from "no items needed"; `checklist.summary.actionable.criteria 17` while `items[].length: 16` with no sentinel for the dropped 17th. Closure: pick one canonical truncation reporter per scope (meta-only / files-array / per-warning slim). Other reporters reference via `seeAlso` rather than independently enumerate. On cross-surface code drift, every project-rooted tool emits the same canonical truncation-reporter set when underlying conditions hold. Add an integration test on a forced-truncation fixture: every truncation event reaches the agent through one named channel. Per AI-first doctrine "Truncation reporters must reconcile across warnings" + "Truncated containers must rename or sentinel."

## Track Q18 — Targeted gap audit (2026-05-07)

Targeted gap audit across `src/mcp/`, `src/reports/`, response-shape sibling files, and the integration test suite — looking for AI-first consumer-doctrine drift not yet captured under Q15/Q16/Q17 and for invariant rules in the doctrine that ship without a pinning integration test. Findings ground out at four shape-level violations (concrete file:line evidence) and two invariant pins (named doctrine rules with no pinning test in `tests/integration/`).

- [ ] **Q18-PARSE-ERROR-REASON-EMPTY-STRING-AMBIGUOUS** `analysisCoverage.parseErrorFiles[].reason` ships `""` when `headError?.message` is falsy at `src/mcp/analysis-coverage.ts:1414` (`reason: truncateParseErrorReason(headError?.message ?? "")`). Sibling fields on the same entry (`naturalParser`, `triggerToken`, `parsedThroughLine`) all use conditional spread to stay present-when-meaningful; `reason` does not. An agent reading a parse-error entry with `reason: ""` cannot distinguish "parser had no message" from "parser truncated to zero chars." Closure: replace the unconditional `reason:` with a conditional spread (`...(reasonText ? { reason: reasonText } : {})`) and add a unit assertion that `reason` is omitted when the parse-error has no message. Per AI-first doctrine "Ambiguous field shapes are dishonest."
- [ ] **Q18-UNTARGETED-CRITERIA-EMPTY-TITLE-LEVEL** Unresolved criterion lookups in `tool-coverage.ts` ship `{ criterionId: id, title: "", level: "" }` at line 1174 and `{ criterionId: id, title: "", level: "", candidates }` at line 1239 — empty strings used as "criterion ID didn't resolve" sentinels. Agent cannot distinguish "criterion exists with no title" from "criterion ID didn't match any loaded standard." Closure: omit unresolved entries from the returned array (safest — keeps the headline count honest), or carry an explicit `resolved: false` discriminator and never emit the empty-string placeholder. Per AI-first doctrine "Ambiguous field shapes are dishonest" — `null`/`""` as unknown sentinel is the canonical mistake the doctrine names.
- [ ] **Q18-EMPTY-WARNINGS-DETAILS-INVARIANT-PIN** No integration test pins the doctrine rule "Empty `warningsDetails.<code>: {}` is dishonest" — the multi-corpus sweep observed `parser_bailed_on_non_jsx_in_tsx_route` and `parser_bailed_zero_findings` shipping `{}` payloads on multiple corpora. Closure: add `tests/integration/warnings-details-non-empty.test.ts` that runs `scan_project`, `scan_file`, `checklist`, `coverage` against a fixture forcing each warning code, then asserts `for code of warnings: warningsDetails[code]` is either populated (file list / count / evidence / reason) OR the code is omitted from `warnings[]` entirely. Pin extends to bootstrap + propose_config surfaces. Per AI-first doctrine warning-channel rule.
- [ ] **Q18-CROSS-SURFACE-REVIEW-CANDIDATE-SHAPE-INVARIANT-PIN** No integration test pins the doctrine rule "Per-tool review-candidate shape must agree across surfaces" — Q-track sweeps documented `priority: null`/`confidence: null` on `scan_file.reviewCandidates[]` while `checklist.items[].candidates[]` populates both, and `coverage.manualWithCandidates[]` strips `candidates: []` entirely. Closure: integration test calls all three surfaces on identical cwd (a fixture with at least 3 manual-review criteria), asserts (a) each candidate's `findingId` is stable across surfaces, (b) `priority` / `confidence` field-presence parity, (c) the candidate identifier hash function is shared. Per AI-first doctrine candidate-shape contract.
- [ ] **Q18-BOOTSTRAP-OUTPUT-SYNTAX-PRECHECK-PIN** Existing bootstrap test (`tests/integration/bootstrap-suggested-config-paste-safe.test.ts`) checks classification predicates but does not lex/parse the generated `ra11y.config.ts` as valid TypeScript before serialization. Doctrine rule "Bootstrap output must be paste-safe" calls out trailing commas, unterminated strings, and mismatched brackets as the canonical regression — the 2026-04-30 sweep observed exactly this pattern. Closure: extend the existing test (or add a sibling) that feeds the bootstrap-emitted config string through `ts.createSourceFile` (or `Bun.Transpiler` for shape-only) and asserts zero parse diagnostics on a corpus with no detectable vendor signal AND on a bulk-vendor corpus. Per AI-first doctrine bootstrap-correctness bar.
- [ ] **Q18-NEXTSTEP-CYCLE-AVOIDANCE-PIN** No integration test pins the doctrine rule "NextStep handoffs must terminate at a narrowing tool, never form a cycle between transport-failing siblings" — the bulk-corpus regression where `checklist.nextStepStructured.tool: "coverage"` while `coverage.nextStepStructured.tool: "checklist"` on the same scope went undetected for an entire sweep. Closure: integration test forces oversize-truncation on a bulk-vendor fixture (≥1000 minified files), runs each project-rooted tool, walks `nextStepStructured.tool` recommendations one hop, asserts the next call EITHER reduces input scope (`restrictToPaths` / `additionalPaths` / narrower `cwd`) OR reduces the rule set — never echoes the parameters that produced the truncation. Per AI-first doctrine cycle-detection invariant.
