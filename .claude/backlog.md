## Track Q16 — Multi-corpus AI-first sweep (2026-05-05)

Second multi-corpus AI-first sweep on four shape-distinct corpora (CSS-framework distribution with documentation site; static-site-generator with mixed Liquid/ERB templates; vanilla-stack catalog of ~50 sibling demo subdirectories; vendor-template bulk catalog of ~100 sibling subdirectories with extensive duplicated vendor JS/CSS). 54 raw findings → 22 after cross-corpus dedupe → 18 actionable after filtering against existing Track Q15 items.

- [ ] **Q16-SCOPE-WARNING-SET-DRIFTS-ACROSS-PROJECT-ROOTED-SURFACES** Corpus-level scope warnings ship from scan_project but vanish on sibling project-rooted tools (checklist / coverage / propose_config) on identical cwd — observed across 3 of 4 corpora. Codes that drift: `truncated_files_dropped`, `response_token_budget_truncated`, `bulk_catalog_detected`, `js_innerhtml_template_literal_unparsed`, `dynamic_content_container_detected`, `linked_stylesheet_external_cdn_skipped`, `scanned_build_artifacts_present`, `source_language_unsupported`, plus dynamic warning payloads like `jsx_code_demo_prop_parsed_as_live_dom`. propose_config ships zero warnings/warningsDetails on a corpus where scan_project flagged 9 distinct concerns. An agent calling checklist or propose_config first has no scope-confidence telemetry that bulk-vendor or template-island conditions exist. Closure: single shared scan-confidence helper consumed by every project-rooted tool (scan_project, checklist, coverage, propose_config, bootstrap). On identical cwd the helper emits the same scope-level warning set across all four; surface-specific truncation codes are the only legitimate divergence. Add an integration test pinning `set(scan_project.warnings) - {surface-specific truncation codes} ⊆ checklist.warnings ∩ coverage.warnings ∩ propose_config.warnings`. Per AI-first doctrine "Per-tool lane and warning-set classification must agree" + "Cross-surface count invariant" — extension to scan-confidence telemetry.
- [ ] **Q16-TRUNCATION-REPORTER-CODE-DRIFT-AND-OVERLAP** Truncation events fire through different codes per surface and overlap within one response — observed across all 4 corpora. Two distinct shape problems: (a) per-surface code drift — scan_project uses `response_token_budget_truncated` + `truncated_files_dropped`, checklist uses `results_truncated_use_nextcursor`, coverage uses `response_dropped_files_oversize`. Identical conceptual event, three distinct names. (b) within-one-response overlap — `response_meta_truncated.fields` and `response_dropped_files_oversize.metaFieldsDropped` both enumerate dropped meta fields with non-aligned counts (e.g. 2 vs 12 entries, partial overlap on `analysisCoverage` / `scannedBuildArtifacts`). Plus per-warning inline `shownCount`/`totalCount` pairs duplicated by `response_dropped_files_oversize.slimTruncations`. Three reporters describing one truncation pass with no canonical channel. Subsumes per-surface name-retention regressions: empty `checklist.items: []` / `coverage.manualWithCandidates: []` under truncation indistinguishable from "no items needed"; `checklist.summary.actionable.criteria 17` while `items[].length: 16` with no sentinel for the dropped 17th. Closure: pick one canonical truncation reporter per scope (meta-only / files-array / per-warning slim). Other reporters reference via `seeAlso` rather than independently enumerate. On cross-surface code drift, every project-rooted tool emits the same canonical truncation-reporter set when underlying conditions hold. Add an integration test on a forced-truncation fixture: every truncation event reaches the agent through one named channel. Per AI-first doctrine "Truncation reporters must reconcile across warnings" + "Truncated containers must rename or sentinel."
- [ ] **Q16-SEVERITY-CONTRADICTS-FRAGMENT-OR-WRAPPER-HEDGE** Document-shaped rules ship `severity: warning|error` on partial-parse / fragment / wrapper-class files where the rule's own reason concedes the predicate may not hold — observed across multiple corpora. (a) `semantics/landmark-main` fires at `severity: warning, confidence: medium` on layout-wrapper / template-partial files (no `<body>`, frontmatter fence, slot/yield directives detected) with `couldBeWrongBecause: ["partial_or_layout_file_requires_composed_check"]` and reason 'Verify against the parent layout or partial chain'. 35 emissions on one corpus, 1 on another. (b) `navigation/href-empty-fragment` fires 44 times at `severity: error, confidence: high` with hedge text 'inside wrapper class=highlight — likely demonstration code, verify the anchor renders for real users before treating as broken' on a documentation corpus. (c) `document/page-titled` ships `severity: error, confidence: low` on a partial-parse file — severity and confidence already disagree on the same finding. (d) wcag22:2.2.2 carousel candidates ship `priority: high` while reasons concede 'pause control may live in sibling file' (extends the same shape to candidate-priority channel). (e) `color/meaning-by-color-only` ships severity:warning on `.carousel-item.active` despite `couldBeWrongBecause` hedge that state_class may have aria sibling. Closure: couple severity to confidence (when `confidence: low`, severity must be info or finding moves to review-candidate). When `couldBeWrongBecause` includes a fragment/composition/demonstration token, downgrade to `severity: warning, confidence: medium` and route to review-candidate, OR downgrade further to `severity: info, confidence: low`. Pin via fixture `tests/fixtures/real-world/landmark-main-on-fragment/`: scan_file on a fragment-classified fixture must not emit document-shaped rules at `severity: error|warning`. Per AI-first doctrine "Reason text and severity must agree" + "Reason / priority / fix-description must agree across all three channels."
- [ ] **Q16-CORPUS-WARNING-NOT-PROPAGATED-TO-PER-FINDING-CONFIDENCE** Per-finding `confidence` ignores corpus-level warnings naming the same files — observed across 2 corpora. (a) On a documentation corpus paired with code-demo MDX: scan_project ships `jsx_code_demo_prop_parsed_as_live_dom` with per-file `matchCount` (e.g. dropdowns.mdx: 28, navbar.mdx: 26, 72 files total). 142 emissions of `aria/dropdown-toggle-triple-aria-missing` and 1284 of `navigation/href-empty-fragment` ship at `severity: warning, confidence: medium, couldBeWrongBecause: null` against those same files. The corpus-level warning says the rule's evidence model is degraded on these files; per-finding emissions don't propagate. (b) Same pattern on `keyboard/handler-missing` where `cross_file_listener_resolution_not_attempted_by_rule` is in `couldBeWrongBecause` but `fix.description` carries 'Cross-file check: grep the selector in your HTML to confirm' at `severity: warning, confidence: medium` — fix-description hedge contradicts severity. (c) Mirror case: `semantics/empty-heading` and `navigation/link-descriptive-text` fire as severity:warning on stripped Liquid `{{ }}` token content (provably can't determine the predicate from the source). Closure: plumb corpus-level warning file lists into per-finding emission — when `finding.path` is in the warning's file list, downgrade `confidence` and append the warning code to `couldBeWrongBecause`. Pin: scan a fixture file that triggers a corpus-level warning; assert findings on that file carry the limitation token in `couldBeWrongBecause`. Per AI-first doctrine "Per-finding confidence must reflect per-rule coverage limitations."
- [ ] **Q16-PROPOSE-CONFIG-NEXTSTEP-DOES-NOT-NARROW** `checklist` and `coverage` both ship `nextStepStructured.tool: "propose_config", args: {}` on truncated bulk-vendor or source-volume corpora — observed across 3 of 4 corpora. propose_config's actual output: (a) on a vanilla-stack catalog ships `suggestedConfig` with three commented `rules:` lines and zero `exclude:` block; (b) on a static-site-generator corpus, `suggestedConfig.exclude` lists 2 already-classified `.min.js` files while truncation was source-lane; (c) on a template-website corpus, `args:{}` means 'rerun on the same cwd', no scope reduction. Following nextStep does not narrow the input set; the agent re-runs scan_project and re-trips truncation. Closure: when checklist/coverage truncate AND `bulk_catalog_detected` or source-lane volume drives truncation, route nextStepStructured to `scan_project({restrictToPaths:[<topDirectory not in suggestedExcludes>]})` directly — skip the propose_config detour. When propose_config IS the right step, pass explicit narrowing args, never `args:{}`. Pin: every cross-tool nextStepStructured.tool recommendation, traced one hop on the same cwd, must reduce input scope or rule set. Per AI-first doctrine "NextStep handoffs must terminate at a narrowing tool, never form a cycle between transport-failing siblings."
- [ ] **Q16-PROPOSE-CONFIG-EXCLUDE-MISSING-FROM-CLASSIFIER** `propose_config` does not consume `default_excluded_artifact_paths` or `bulk_catalog_detected.suggestedExcludes` from the shared classifier — observed across 2 corpora. (b) On a template-website bulk catalog, `warningsDetails.bulk_catalog_detected.suggestedExcludes` is 5 globs that would collapse 600+ vendor copies; propose_config.suggestedConfig.exclude ships 954 individual file paths reachable via the same 5 globs. Two emitter paths disagree on dedup shape. Closure: propose_config consumes the same shared classifier output as the warning emitters. When `default_excluded_artifact_paths` or `bulk_catalog_detected.suggestedExcludes` are populated, the exclude block in suggestedConfig contains those globs by construction. Pin: when scan_project ships either signal, propose_config.suggestedConfig.exclude contains the same glob set (paths only when no glob collapses). Pairs with Q15-VENDOR-FILE-SHA-FINGERPRINT-DEDUP-ACROSS-TEMPLATE-SUBDIRS. Per AI-first doctrine "Bootstrap output must be paste-safe" + "Sibling fields naming the same concept must use one shape."
- [ ] **Q16-PROJECT-VS-FILE-FINDING-COUNT-DRIFT-SAME-PATH** `scan_project.plan.findingsByFile[entry].count` disagrees with `scan_file({path: same file}).totalFindings` on identical path — observed on an MDX-heavy documentation corpus: 252 vs 264 (~5% drift). ## Track Q17 — Multi-corpus AI-first sweep (2026-05-06)

Third multi-corpus AI-first sweep on four shape-distinct corpora (vendor-heavy CSS framework with SCSS + JS; Ruby static-site generator with template directives; tutorial-style HTML/CSS/JS collection; bulk HTML template catalog with vendor-heavy admin theme). 5 angles per corpus (scan_project / checklist / coverage / suggest_fix / bootstrap+detect_native_wrappers) returning structured JSON. ~80 raw findings → ~14 actionable after dedupe against Q15 + Q16 (the bulk of repeat findings — empty warningsDetails payloads, cross-surface meta drift, truncation reporter overlap, per-finding fixClass-vs-kind drift, severity-vs-conceded-uncertainty — confirmed reproduction on all four corpora and remain captured under the open Q16 items).

- [ ] **Q17-BOOTSTRAP-WRAPPERS-STRIPS-DISCRIMINATORS** `bootstrap.wrappers` ships `{candidates: []}` only — bare empty array, no disambiguating reason. `detect_native_wrappers` on identical cwd ships `{candidates, emptyReason, projectKind, inapplicable, opaqueCustomComponentNames}`. Cross-corpus all 4 sweep targets. The discriminators that distinguish "tool doesn't apply on this projectKind" from "ran clean / coverage miss" are dropped on the bootstrap surface; agent calling bootstrap first cannot tell whether the empty wrappers list is honest or a coverage gap. Closure: `bootstrap.wrappers` echoes the full `detect_native_wrappers` shape (candidates + inapplicable + projectKind + emptyReason + opaqueCustomComponentNames) via the shared candidate-shape helper; pin via integration test on identical cwd. Per AI-first doctrine "Bootstrap-class lanes must equal project-rooted lanes" + "Per-tool review-candidate shape must agree across surfaces."
- [ ] **Q17-DEFAULT-EXCLUDED-HTML-NO-WARNING** On a tutorial-style HTML/CSS/JS collection, `analysisCoverage.excludedByPatternByExtension['.html']: 7` — 7 of 8 candidate HTML files default-excluded by pattern. No top-level warning surfaces the event; only the meta sub-field exposes it. The `binary_assets_skipped` warning fires for `.png`/`.jpg`/`.mp3`/`.mp4` (much lower-leverage), while the `.html` exclusion (the dominant scope-classifier event on this corpus) is silent at the warnings channel. Agent calling `scan_project` reads 13 findings on the README and concludes "clean tutorial corpus" when the actual lessons (the HTML pages) never reached any rule. Closure: emit a structured `text_source_excluded_by_default_pattern` warning when default-exclude removes a non-trivial count of parser-routable extensions (`.html`/`.css`/`.tsx`/`.jsx`/`.vue`/`.svelte`), with `warningsDetails` carrying the file list and the matching predicate so the agent can scope around via `additionalPaths` / `restrictToPaths`. Per AI-first doctrine "Routing skips that drop content are the symmetric twin of suppression" — extended to default-pattern exclusions of parser-routable extensions.
- [ ] **Q17-SUMMARYONLY-OVERSIZE-NO-WARNING** `scan_project({summaryOnly: true})` is documented as the explicit opt-in shortcut for bulk-corpus first-call ergonomics on catalogs that exceed the host token cap. Observed: on a vendor-heavy CSS framework corpus, the standard envelope ships 82k chars (transport-fail), and the `summaryOnly: true` envelope still ships 54k chars (still exceeds host cap, transport-fail) — but its `warnings[]` includes neither `response_token_budget_truncated` nor `response_dropped_files_oversize`. The summaryOnly path silently succeeds-then-transport-fails with no signal telling the caller to scope down further. Closure: apply the pre-serialization size sentinel + minimum-honest-envelope on the summaryOnly branch too; emit `response_dropped_files_oversize` (or a dedicated `summary_envelope_still_oversize`) when the summary still exceeds the cap. The summaryOnly path is supposed to be the fallback — when even that fails, the agent needs an honest signal. Per AI-first doctrine "Oversize-success is ambiguous failure."
- [ ] **Q17-SUGGEST-FIX-CRITERION-ID-RULE-NOT-FOUND** `suggest_fix({ruleId: "wcag22:1.3.6", file, line})` returns `{error: "No rule satisfies criterion 'wcag22:1.3.6'.", code: "rule-not-found"}` when no rule is registered for the criterion — yet the `checklist` review-candidate ships `criteria: ["wcag22:1.3.6"]` as an addressable item the agent is supposed to walk. The doctrine explicitly says callers may pass either ruleId or criterionId; the per-call surface must address every candidate the manual-review surface ships. Closure: when a candidate's `criteria[]` contains a criterion no rule satisfies, `suggest_fix` should return `kind: "guidance"` framed as "manual-review only — this criterion has no automated rule; verify against [normative quote] manually" instead of the rule-not-found error. OR the candidate shape must split `criteria` into `resolvableByRule[]` vs `manualOnly[]` so the agent can distinguish at the candidate level which calls are addressable. Per AI-first doctrine "Suppress-recommended is a distinct discriminator from guidance" — extended: criteria-without-rule should have a discriminator too.
- [ ] **Q17-CHECKLIST-COVERAGE-NO-MINIMUM-HONEST-ENVELOPE** `checklist` and `coverage` lack the minimum-honest envelope fallback that `scan_project` uses on bulk-vendor corpora (where `summaryOnly: true` / `pageClipReason: "token_density"` shrink the envelope while keeping `plan` + `meta` + `warnings` + `nextStep`). Observed: on a Ruby SSG corpus and on a bulk admin template catalog, both `checklist` and `coverage` ship oversize envelopes (90k+ chars) that transport-fail at the host layer — agent receives only the host-level transport error, no `summary`, no `warnings`, no `nextStep`. The asymmetry: `scan_project` succeeds with a slim envelope + warning; `checklist` / `coverage` succeed-then-evaporate. Closure: checklist and coverage adopt the same minimum-honest envelope policy — under oversize, drop `items[].candidates[]` beyond a per-criterion ceiling (or drop `manualWithCandidates[].candidates[]`), retain summary + warnings + nextStep, emit `response_dropped_files_oversize` (or `response_dropped_candidates_oversize`) so the agent re-scopes via `scan_project({restrictToPaths})`. Per AI-first doctrine "Oversize-success is ambiguous failure" — extension to manual-review surfaces.
